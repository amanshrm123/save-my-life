# Architecture Decision: Restricted Social Share Targets (v5)

Founder ask (recorded, deferred from the UI-only pass): "Card sharing will only happen for platforms such as Instagram story, WhatsApp status and facebook story."

Founder-confirmed decisions (this pass, not open for re-litigation):
- **Ship now, dim Instagram/Facebook until the founder supplies a Meta App ID.** WhatsApp Status works immediately, no registration needed.
- **Keep the "More…" text-link fallback** below the 3 tiles (web builds and users missing all 3 apps still have a path to share).

## 1. Root cause of the founder's report

The founder's emulator/device almost certainly has none of the 3 apps installed. `share_plus` shows whatever resolves `ACTION_SEND`. This change will not make Instagram appear on a bare emulator either — verification requires a device with all 3 apps installed and signed in. The design below deliberately shows all 3 brand tiles even when uninstalled (dimmed), so wiring can be visually confirmed even without the apps present.

## 2. Platform capability findings (researched, not assumed)

### 2.1 Instagram Stories — viable, but gated on a Meta App ID

| Item | Value |
|---|---|
| Action | `com.instagram.share.ADD_TO_STORY` |
| Package | `com.instagram.android` |
| **Required extra** | `source_application` = Facebook App ID (String) |
| Background asset | `setDataAndType(uri, "image/jpeg")`, min 720×1280, 9:16 |
| Sticker asset | `interactive_asset_uri` (Uri) |
| Background fill | `top_background_color`, `bottom_background_color` (hex strings) |
| URI | must be `content://`, plus `FLAG_GRANT_READ_URI_PERMISSION` *and* an explicit `grantUriPermission("com.instagram.android", uri, …)` |
| Install check | `packageManager.resolveActivity(intent, 0) != null` |

The App ID has been mandatory since January 2023. Omit it and Meta shows *"The app you shared from doesn't currently support sharing to Stories."* No Meta app review is needed for basic story sharing — the App ID is just an attribution key. (The "Shared from…" attribution watermark *is* partner-review-gated; not needed here.)

### 2.2 Facebook Stories — same shape, same gate

| Item | Value |
|---|---|
| Action | `com.facebook.stories.ADD_TO_STORY` |
| Package | `com.facebook.katana` |
| **Required extra** | `com.facebook.platform.extra.APPLICATION_ID` = FB App ID |
| MIME | `image/jpeg` |
| Sticker / colors | `interactive_asset_uri`, `top_background_color`, `bottom_background_color` |
| Constraint | must pass a background asset, a sticker asset, or both |

Same `content://` + `grantUriPermission("com.facebook.katana", …)` requirement.

### 2.3 WhatsApp Status — an official API exists (no registration needed)

| Item | Value | Confidence |
|---|---|---|
| Action | `Intent.ACTION_VIEW` | High |
| Data | `Uri.parse("https://wa.me/status")` | High |
| Package | `com.whatsapp` | High |
| Extra | `share_type` = `"SHARE_TO_STATUS"` | High |
| Extra | `source_app_package_name` = our own package | Medium |
| Background media | `Intent.EXTRA_STREAM` (content Uri) | High |
| Foreground/sticker | `foreground_media` (content Uri) | Medium |
| Registration | None. No Meta App ID. | High |

flutter-developer must verify the exact spelling of `source_app_package_name` and `foreground_media` against the live WhatsApp FAQ page and the `fbsamples/whatsapp_status_api_android` sample repo before implementing. The action/URI/`share_type`/package are confirmed by multiple independent sources.

**This is the single most important finding: WhatsApp needs zero external registration and can ship immediately; Instagram and Facebook are blocked on an ops prerequisite (founder-confirmed to ship dimmed until then).**

## 3. Composition: sticker-on-gradient, not background

The outcome card is a rounded-rect card, not a 9:16 frame. Passed as a *background* asset it gets center-cropped or letterboxed by all three composers — hides the card's own shadow/border, which is the visual identity.

**Decision:** pass the card PNG as the **sticker** layer (`interactive_asset_uri` / `foreground_media`) over a **tier-colored gradient** (`top_background_color` / `bottom_background_color` from the existing `AppColors.red` / `.green` / `.gold` per `RunOutcome`, paired with `AppColors.ink`). Use the existing constants; do not invent hex values.

Why:
- All three targets support this identical composition — one intent shape, one code path.
- `_EntranceCard._shadowInset = 32` in `lib/features/outcome/presentation/outcome_card_screen.dart` already bakes a transparent margin into the exported PNG — exactly what a sticker layer needs. Zero renderer changes for composition.
- Sticker layers are user-movable in the composer, reading as premium rather than a screenshot dump.

Verify-during-implementation: sticker-only sharing (no background asset) is documented as using `setType("image/*")` rather than `setDataAndType(...)` — medium confidence on that specific detail. If sticker-only misbehaves, the documented fallback is background-mode with the same background colors for letterbox fill. Don't block on it.

## 4. Custom in-app 3-tile picker (the OS sheet cannot satisfy the ask)

The generic system sheet's contents are user-installed-app-dependent and unfilterable. "Only these 3" therefore requires our own UI.

**New flow** — replaces the direct `shareService.shareFile` call in `_onShare`:

1. Share / "Flex it" tapped. Button label, styling, and the `_isSettled` enabled-gate are unchanged.
2. `CardRenderer.renderToFile` runs — once per Share tap, before the sheet opens. On `null`, abort silently (preserves today's behavior).
3. Probe installed targets via the new MethodChannel.
4. Show `ShareTargetSheet`: a modal bottom sheet over the still-mounted card.
5. Tap a tile → fire that target's intent → dismiss sheet.

`ShareTargetSheet` spec (for game-ux-designer):
- Modal bottom sheet, `AppColors.paper`, 2.5px `AppColors.ink` border, 20px top radius, hard zero-blur offset shadow — reuse the sticker-button visual language, introduce no new vocabulary.
- Title "Share your card" (Fredoka).
- Row of 3 equal tiles, 72×72, ink border 2.5, rest shadow offset 5. Order: Instagram, WhatsApp, Facebook.
- Each tile has a two-line label: brand name + surface — "Instagram / Story", "WhatsApp / Status", "Facebook / Story". The second line is load-bearing: it sets the expectation that this lands in a Story/Status composer, not a DM.
- `AppTypography.ghostLink` "More…" below the row — same convention as the existing "Home" link on the outcome screen.

### 4.1 "More…" escape hatch — founder-confirmed, keep

- Web is an active dev target. Android intents don't exist there. Instagram has no web story-composer URL, so an Instagram tile on web could only open instagram.com — strictly worse than the Web Share API.
- Users with none of the 3 installed hit a total dead end otherwise.
- Cost is zero — `ShareService` already exists and stays untouched.
- The founder's intent (privilege broad-audience Story/Status surfaces over DMs) is fully served by giving the 3 the visual real estate; "More…" is a de-emphasized text link, not a peer.

**Web decision:** platform-gate on `kIsWeb`. On web, Share goes straight to the existing `share_plus` path and the 3-tile sheet is never shown. Do not ship a fake 3-icon row that can't work.

## 5. Custom platform channel. Reject `appinio_social_share`.

Disqualifying, in order:
1. It requires `MANAGE_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE` and `READ_MEDIA_*` in the manifest. `MANAGE_EXTERNAL_STORAGE` is a Play policy-restricted permission needing a declaration form and justification, and games get rejected for it routinely. Our approach needs zero storage permissions — `content://` + FileProvider grants are permission-free. This alone ends the discussion.
2. Its WhatsApp method is a generic WhatsApp share, not the Status API — it doesn't deliver the actual ask.
3. Last published ~24 months ago (0.3.2), 140 pub points — behind this app's Flutter/AGP cadence.
4. Drags in Twitter/TikTok/Telegram/Messenger/SMS surface actively not wanted.
5. The native surface needed is genuinely tiny: one `MethodChannel`, three intent builders, one `resolveActivity` probe — roughly 120 lines of Kotlin. Consistent with this app's existing posture of taking dependencies only where the native surface is non-trivial.

**Keep `share_plus`** for the "More…" path and for web. Do not remove it.

## 6. FileProvider: a new one is required — share_plus's cannot be reused

`share_plus` merges in a provider with authority `${applicationId}.flutter.share_provider`, but its paths config (`share_plus-13.3.0/android/src/main/res/xml/flutter_share_file_paths.xml`) exposes only:

```xml
<cache-path name="cache" path="share_plus/" />
```

`CardRenderer` writes to `getTemporaryDirectory()` root (= `getCacheDir()`), which is outside that path. share_plus works today only because it copies the file into its own private `caches/share_plus/` subdir first. Squatting on another plugin's private authority would break silently on upgrade. Rejected.

**Add** to `android/app/src/main/AndroidManifest.xml`, inside `<application>`:
- `androidx.core.content.FileProvider`, authority `${applicationId}.shareprovider` (resolves to `com.timingtap.timing_tap.shareprovider`), `android:exported="false"`, `android:grantUriPermissions="true"`, meta-data `android.support.FILE_PROVIDER_PATHS` → `@xml/share_file_paths`.

**Add** `android/app/src/main/res/xml/share_file_paths.xml` with `<cache-path name="share" path="share/" />`.

**Change** `CardRenderer` to write to `<getTemporaryDirectory()>/share/share_card.png`, creating the dir if absent. Keep the single fixed filename — that overwrite is what stops cache files accumulating. No collision with `share_plus/`, and the "More…" path still works (share_plus takes a raw path and copies).

No new Gradle dependency: `androidx.core` is already on the classpath via the Flutter embedding.

## 7. Package visibility — hard Android 11+ requirement

`targetSdk = flutter.targetSdkVersion` (≥30), so package-visibility filtering applies: both `resolveActivity` and `setPackage` silently fail for undeclared packages. Add to the existing `<queries>` block in the manifest:

```xml
<package android:name="com.instagram.android" />
<package android:name="com.facebook.katana" />
<package android:name="com.whatsapp" />
```

Do not use `QUERY_ALL_PACKAGES` — that's the policy-restricted one. Targeted `<package>` declarations are permitted and need no declaration form.

## 8. Fallback behavior per target

**Decision: visible-but-dimmed tile at 0.45 opacity, tap → toast.**

Matches this app's one established disabled affordance exactly — `StickerButton` uses `Opacity(opacity: _interactive ? 1 : 0.45)` (`lib/core/widgets/sticker_button.dart:177`), and the outcome screen already documents 0.45 as the convention. A fixed 3-tile row also keeps layout stable and keeps all 3 brands visible.

Rejected: Play Store redirect (pushing a player out of the game to install Instagram mid-session is a retention leak). Rejected: hiding tiles (reflowing 3→1 tile makes the sheet look broken and hides the feature).

Feedback rules:

| Case | Behavior |
|---|---|
| Direct intent launched OK | Dismiss sheet, no toast |
| `ActivityNotFoundException` | Toast "Couldn't open Instagram" |
| Pre-checked not installed | Dimmed tile; tap → toast "Instagram isn't installed" |
| "More…" path | Existing "✓ Shared" toast, on real `ShareResultStatus.success` |

`startActivity` succeeding only means the composer opened — not that anything was posted. Firing "✓ Shared" on a direct intent is a false claim, and it'd surface as a stale toast when the user returns to the app minutes later. Reuse the existing `_ShareToast` widget for the error strings; new copy belongs in `lib/core/copy/app_copy.dart`.

## 9. Meta App ID handling and phasing (founder-confirmed: ship now, dim until provided)

WhatsApp needs nothing. Instagram and Facebook need a Facebook App ID.

**Decision:** inject via `--dart-define=FB_APP_ID=...`, read with `String.fromEnvironment('FB_APP_ID')`, plumbed through the MethodChannel. Never hardcoded, never committed. When the App ID is empty at build time, treat the Instagram and Facebook tiles exactly as "not installed" (dimmed). A dev build without the define then degrades gracefully instead of surfacing Meta's *"doesn't currently support sharing to Stories"* error dialog.

**Phase 5a (this round):** sheet + all 3 tiles + WhatsApp Status live end-to-end. Instagram/Facebook wired but dimmed until the define is supplied.
**Phase 5b (unblocks itself):** founder supplies the App ID; no code change, IG/FB light up.

## 11. Memory / lifecycle (CLAUDE.md rule 7)

Confirmed trivially safe, and strictly better than today:

- One-shot `startActivity`. No listener, no receiver, no callback registration, nothing retained. `share_plus` currently registers a `SharePlusPendingIntent` broadcast receiver to learn the chosen component — the direct-intent path registers nothing, so it retains less than the current implementation.
- The MethodChannel handler registers once per process in `MainActivity`. Constant cost, not per-share.
- `installedTargets()` returns a 3-element `List<String>`. Use a `FutureProvider.autoDispose` scoped to the sheet so it's collected on dismiss. Probe once on sheet open — not per rebuild, and not in a keep-alive provider (install state can change between sessions). `PackageManager.resolveActivity` allocates a transient `ResolveInfo`; no retention.
- The one real memory item is pre-existing and must stay bounded: `CardRenderer` transiently holds a ~1020×1500 RGBA `ui.Image` (~6 MB) plus its PNG `ByteData`. Already disposed in `finally`. The invariant this change must not break: exactly one render per Share tap, even though the user can now try multiple targets from one sheet. The single file is reused across tiles. Re-rendering per tile tap would multiply peak RAM by the number of taps — do not do it.
- Keep the single fixed `share_card.png` filename after the directory move, so cache files never accumulate.
- While the user is in Instagram our activity may be trimmed and the cache file could in principle be evicted — harmless, the receiving app consumes the URI grant at intent-delivery time. No mitigation needed.

## 12. Flags for downstream pipeline stages

**code-reviewer:**
1. "✓ Shared" toast must not fire on direct-intent paths (intent launch ≠ post published).
2. Single-render invariant: one `renderToFile` per Share tap, not per tile tap.
3. `mounted` guard around the new `installedTargets()` await before showing the sheet.
4. The existing `_sharing` re-entrancy bool must now also cover "sheet is open" — a double-tap must not stack two sheets.
5. Both `FLAG_GRANT_READ_URI_PERMISSION` and an explicit `grantUriPermission(targetPackage, …)` before `startActivity`. Both, not either.
6. No `QUERY_ALL_PACKAGES`; no storage permissions introduced.
7. FB App ID from `--dart-define` only — never a committed constant.
8. Kotlin: `resolveActivity` returns null both when the app is absent and when the package is missing from `<queries>`. Don't let a `<queries>` regression silently masquerade as "nothing installed."

**play-store-specialist:**
1. Confirm the 3 targeted `<queries><package>` entries need no permissions declaration form under current policy, and aren't read as installed-app fingerprinting.
2. Confirm no storage permission is introduced.
3. Data Safety form: does firing a share intent with a rendered image constitute "Photos and videos — shared with third parties," or does the user-initiated-sharing exemption apply?
4. Meta App ID shipped in the APK is a public identifier, not a secret — confirm no policy issue.
5. Brand assets: in-app Instagram/WhatsApp/Facebook icons must be Meta's official assets with correct color and clear-space, and must not imply endorsement. Applies to store screenshots too.

**app-store-specialist:** iOS deferred (no Apple ID yet). For the record so it isn't re-litigated later: iOS uses custom URL schemes (`instagram-stories://share?source_application=<appid>`, `facebook-stories://share`, and pasteboard-based handoff for WhatsApp) plus `LSApplicationQueriesSchemes` entries in `Info.plist`. This design keeps that a pure-native addition.

**game-ux-designer:** needs a mockup for `ShareTargetSheet` — tile geometry, official brand icon assets, the 0.45 dimmed state, both toast strings, and "More…" placement. Per CLAUDE.md rule 6, must verify the built sheet matches the mockup before this is done.

**tester:** scope = the sheet + intent dispatch only, not the whole outcome flow. Unit-testable: `ShareTarget` → intent-args mapping, install-state → tile state, empty-App-ID → dimmed. Mock the channel with `TestDefaultBinaryMessengerBinding`. A real intent can't be integration-tested — assert on recorded MethodChannel invocations.
