# Architecture v1

*Living document. This is the current agreed architecture for the Timing-Tap feel-first launch. Revisions are **not** edited in place — a new agreed version lands as `docs/architecture/v2.md`, `v3.md`, etc., and this file is superseded. Source of truth for design: `docs/discovery/TimingTap_Discovery_v1.md`; source of truth for launch scope/timeline: `docs/discovery/TimingTap_OnePager_v1.md`.*

---

## 0. What this document is

The concrete, buildable technical architecture for the **15–20 day feel-first playable** defined in the One-Pager. It is scoped to answer exactly one question — *does the tap feel good enough that a stranger replays unprompted and comes back on D1?* — and nothing else. Every decision below is optimized for that, for a solo/small team, and against the hard timeline. Where I had a choice, I made the call and justified it; there are no unresolved "option A vs option B" left for someone else to decide.

## 1. Tech stack decisions

### 1.1 Framework
**Flutter (stable channel), Dart 3, single codebase, Android target first.** Play Store first is a locked deadline-protection decision (One-Pager risk #1). The code is fully cross-platform; iOS is a build-target flip in Phase 6, not a rewrite.

### 1.2 Timing engine — the one part that cannot be wrong

This is the highest-risk subsystem (Discovery §3a is non-negotiable). The architecture enforces the three correctness rules structurally so they can't be accidentally violated:

- **Input capture: raw pointer, not gesture, not render tick.** Wrap the tap surface in a **`Listener` widget** and read the timestamp in `onPointerDown`. Do **not** use `GestureDetector.onTap` (adds arena-resolution delay) and do **not** read the clock in a `build`/`Ticker`/`AnimationController` callback (injects up to a full 16.7 ms frame of error and can flip a Perfect into a Miss). The timestamp is taken as the very first statement inside `onPointerDown`.
- **Clock: monotonic only.** A single `MonotonicClock` wrapper around Dart `Stopwatch` (`core/clock.dart`). `DateTime.now()` is **banned** in the timing path — enforce with a lint/code-review rule (code-reviewer agent owns this check). The run starts the stopwatch; every tap reads `stopwatch.elapsedMicroseconds`. Microsecond resolution, so band math (±30 / ±80 ms) is never quantized by our own code.
- **Consistent latency path.** The moving countdown/target indicator is rendered with a **`CustomPainter` driven by a single `Ticker`**, reading elapsed time from the *same* `MonotonicClock` instance the tap measurement uses. Display and measurement share one clock, so device display latency is a constant offset, not drifting noise (Discovery §3a rule 3). We do **not** rebuild the widget tree per frame for the moving element — `CustomPainter` repaints only the indicator layer, keeping the input→render path tight and jank-free.

**Widget tree vs CustomPainter — the call:** *Hybrid.* Static UI (life bar, target-time label, buttons, cards) stays plain widgets — it's UI-driven, cheap, and lets the game-ux-designer and flutter-developer iterate fast. Only the time-critical moving indicator uses `CustomPainter` + `Ticker`. We do **not** pull in Flame or any game engine: this is a UI-driven 2D game with one moving element and card screens; Flame's scene/sprite/game-loop machinery is pure overhead here and would slow the Gate-1 prototype. Flutter's own render pipeline is the right tool.

The timing engine exposes one pure function testable in isolation:
`TapResult resolve({required int targetMicros, required int pressMicros, required double lifePct})` → returns `{band: perfect|onPoint|miss, deltaMs, lifeDelta}`. Band thresholds and the adaptive coefficient live in a single `TimingConfig` constants object (Phase 0 playtest fills in the real ms values). This makes the whole engine unit-testable by the tester agent without a device.

### 1.3 State management — **Riverpod** (`flutter_riverpod`)

The state here is genuinely simple: current life %, run phase, streak, loss counters, last outcome. That argues against anything heavy.

- **Not Bloc** — event/state boilerplate is disproportionate to this state size and slows a 20-day build.
- **Not raw `setState`** — it would entangle the timing engine and persistence with the widget layer, making the engine untestable in isolation (and the engine is the thing we most need to test).
- **Riverpod (chosen)** — gives compile-safe dependency injection and provider overrides, which is exactly what we need to (a) keep the timing engine and repositories decoupled from the UI, (b) mock the clock/persistence in tests, and (c) let the tester agent drive the run state machine headlessly. Minimal boilerplate, no `BuildContext` coupling. Use plain providers/`NotifierProvider` — **no** codegen, **no** hooks; keep it lean.

`RunController` (a `Notifier`) is the single owner of run state and the only thing that mutates life/outcome. Everything else reads from it.

### 1.4 Local persistence — **Hive** (`hive` + `hive_flutter`)

Local-first is a hard requirement (Discovery §5); the game must ship 100% offline. Persisted data is small and simple: lifetime + best-streak counters, daily-streak state + last-play date, and a `Set<String>` of seen card IDs (for variety).

- **Not `shared_preferences`** — fine for the counters, but awkward for the seen-cards set and gives no structure; we'd outgrow it immediately.
- **Not Isar** — more capable (queries/indexes) but heavier, needs codegen, and carries real maintenance-uncertainty risk. We have no query needs. Overkill.
- **Hive (chosen)** — pure-Dart, fast, no native deps, near-zero boilerplate, trivial to open in `main()` before `runApp`. Perfect fit for a handful of typed boxes. Access is wrapped behind a `ProfileRepository` interface so the storage engine is swappable and mockable in tests.

### 1.5 Card rendering for the share pipeline — **`RepaintBoundary` capture (WYSIWYG)**

The outcome card is built as a **normal Flutter widget** — one `CardTemplate` widget that takes `(outcomeType, bodyText, artVariant, lossCount)` and lays them out. To share, wrap that same widget in a `RepaintBoundary` (rendered offscreen at a fixed export size), call `boundary.toImage()` → PNG bytes.

- **Not manual `Canvas` compositing** — reimplementing text layout/wrapping/emoji on a raw canvas is slow to build and a bug farm, for zero benefit here.
- **RepaintBoundary (chosen)** — the shared image is pixel-identical to what the player saw on screen (WYSIWYG), and it directly realizes the Discovery §4 "one template + text pool + few art variants" model: 30–50 cards = 30–50 data rows through **one** widget, not 50 assets. This is the template engine.

### 1.6 Firebase scope — **Analytics only for the v1 launch**

Explicit reconciliation of a tension between the two docs: Discovery §5 recommends *analytics + remote config*; the One-Pager (the committed launch plan) lists **Remote Config as OUT** and only **Analytics as IN**. The One-Pager wins for launch scope.

- **v1 launch: Firebase Analytics only.** It is the single cloud piece, and it exists solely to measure the one launch metric — **D1 retention** — plus the watch-only secondaries (replays/session, share taps/death, session length). No accounts, no auth, no Firestore, no functions. This is **not** a backend-heavy game; there is no custom backend at all.
- **Remote Config: deferred to v1.1**, exactly as the One-Pager mandates — but architected-for now. The card content loads through a `CardContentSource` interface with a `BundledCardSource` (reads a bundled JSON asset) implementation for v1. Remote Config drops in later as a second implementation with **zero refactor** to the outcome system. That's the whole cost of "ready for it" — one interface, taken now.

Analytics events are centralized in one `AnalyticsEvents` file (no string literals scattered in features) so the tester and analytics-consumer can see the full event contract in one place. Minimum event set: `install`, `app_open`, `run_start`, `run_end{outcome, losses, deltaMsAvg}`, `card_shown{cardId}`, `share_tapped{cardId}`, `interstitial_shown`.

### 1.7 Ad mediation — **AdMob direct (`google_mobile_ads`), no mediation layer**

Discovery §6 says "assume AdMob or AppLovin MAX." The call: **plain AdMob, no mediation SDK.**

v1 ships exactly **one** placement — a single frequency-capped interstitial (One-Pager IN list; banners/rewarded are OUT). Mediation (AppLovin MAX) only earns its complexity when you're arbitraging multiple ad networks at scale — that's a v2+ revenue-optimization problem, and revenue is explicitly *not* a launch metric. Adding a mediation SDK now buys integration/config overhead and review-surface risk for no launch value. AppLovin MAX is the right migration when scaling monetization post-PMF; the ad code is wrapped behind an `AdService` interface so that swap is contained. AdMob also aligns with the Google/Play-first launch and the Firebase stack already in use.

`AdService` owns the frequency cap (every 3–4 runs / ≤ once per 2–3 min) and **preloads the next interstitial behind the outcome card** so dismissing drops straight into the next run. Hard rule enforced in code: the interstitial can only be requested on the run→run transition **after** the outcome card + share moment, and **never** over the play surface or the outcome/death card.

### 1.8 Instagram Stories share — **`share_plus` native share sheet (primary), IG Stories deep-link as best-effort**

Discovery §4/§5 and the One-Pager both specify: render card → native share sheet → Instagram Stories deep-link.

- **Primary, guaranteed path:** write the PNG to a temp file and hand it to **`share_plus`** (native OS share sheet). This works on both platforms, needs no per-app entitlements, and the user picks Instagram (or anything else). This is the shipping path for v1 — reliable and low-risk against the deadline.
- **Best-effort enhancement:** if Instagram is installed, offer a direct `instagram-stories://share` deep-link (pass the PNG as the Stories background via pasteboard on iOS / intent extras on Android). Behind a capability check; if it fails, silently fall back to the share sheet. This is *nice-to-have within Phase 3* and must never block it — direct programmatic IG posting is no longer allowed for third-party apps anyway, so the share sheet is the honest primary.

## 2. Module / package architecture

Flat, feature-first, deliberately small. No speculative abstractions — the only two "interfaces for later" (`CardContentSource`, `AdService`) are justified above and cost one file each. Everything lives under `lib/`.

```
lib/
  main.dart                      # Hive init, Firebase init, runApp
  app/
    app.dart                     # root widget, theme, ProviderScope
    router.dart                  # 3 screens: Play, Outcome, (Menu/Settings-lite)
  core/
    clock.dart                   # MonotonicClock (Stopwatch wrapper) — the only clock
    timing_config.dart           # band thresholds, life deltas, adaptive k (Phase 0 values)
    theme.dart, constants.dart
  features/
    timing_engine/
      timing_engine.dart         # pure resolve(): (target,press,life) -> TapResult
      tap_surface.dart           # Listener(onPointerDown) capture widget
      indicator_painter.dart     # CustomPainter + Ticker, reads MonotonicClock
    run/                         # == the outcome_system
      run_controller.dart        # Notifier: owns life%, phase, streak; applies TapResult
      outcome_resolver.dart      # pure: run state -> Death | Survived | EternalHuman
      run_state.dart             # models
    cards/
      card_content_source.dart   # interface (BundledCardSource for v1; RemoteConfig later)
      bundled_card_source.dart   # reads assets/cards.json
      card_picker.dart           # pick unseen card for outcome pool
      card_template.dart         # ONE widget -> all cards (the template engine)
    share/                       # == share_pipeline
      card_capture.dart          # RepaintBoundary -> PNG bytes
      share_service.dart         # share_plus + IG Stories deep-link fallback
    ads/
      ad_service.dart            # interface + AdMob impl; frequency cap + preload
    analytics/
      analytics_service.dart     # Firebase Analytics wrapper
      analytics_events.dart      # centralized event contract
    persistence/
      profile_repository.dart    # interface
      hive_profile_repository.dart
    daily_streak/
      daily_streak_controller.dart  # streak count + last-play-date logic
assets/
  cards.json                     # 30–50 death + small Survived + Eternal pools
  art/                           # few reusable art variants
```

### Data flow (one run)

```
TapSurface(onPointerDown → MonotonicClock.micros)
        → RunController.registerTap(pressMicros)
                → TimingEngine.resolve(target, press, life)  [pure]
                → applies lifeDelta, updates life%/phase
                → OutcomeResolver.check(runState)  [pure]
        ── if run continues → next target (loop)
        ── if run ends:
              → CardPicker.pick(outcome) via CardContentSource
              → OUTCOME SCREEN shows CardTemplate + "after N deaths"
              → AnalyticsService.runEnd(...) , card_shown
              → [player taps Share] → CardCapture(RepaintBoundary→PNG)
                                     → ShareService (share sheet / IG)
                                     → Analytics.share_tapped
              → ProfileRepository.record(outcome, losses)   [Hive]
              → DailyStreakController.touch()                [Hive]
              → [Next] → AdService.maybeShowInterstitial()   [freq-capped, preloaded]
                       → RunController.startNewRun()
```

Dependency rule: features depend **downward** on `core` and on repository/service *interfaces* only; nothing depends on Firebase/AdMob/Hive concretes except their own wrapper. This keeps the timing engine and run logic pure and headlessly testable.

## 3. Phase-wise development plan (maps 1:1 onto the One-Pager timeline)

Agents referenced: **flutter-developer** (client), **backend-engineer** (Firebase/cloud), **game-ux-designer** (UX/flows), **tester** (QA), **code-reviewer**, **player-reviewer** (fun/feel), **play-store-specialist** / **app-store-specialist** (store compliance).

### Days 1–2 — Walking skeleton + timing engine
- **Build:** `core/clock.dart`, `timing_config.dart`, `timing_engine.dart` (pure resolve), `tap_surface.dart` (Listener capture), `indicator_painter.dart`. One bare Play screen: random target time shown, tap registers, delta + band printed on screen. Riverpod `ProviderScope` + skeletal `RunController`. No cards, no persistence, no art.
- **Owns:** flutter-developer (lead). game-ux-designer sketches the Play-screen layout (target display + tap zone + life bar) so the prototype is legible. code-reviewer enforces the two hard rules: monotonic clock only, timestamp-in-`onPointerDown`.
- **Done when:** on a real Android device, a tap prints a stable delta and a Perfect/On-point/Miss band, and repeated taps show consistent latency (no per-frame drift). The `resolve()` unit tests pass (tester).

### Days 3–5 — Feel prototype + **GATE 1 (kill/continue)**
- **Build:** life bar wired to band results; adaptive tightening *scaffolded but off* (fixed bands ship per One-Pager OUT list — see §4); on-device tuning of the actual ±ms values into `timing_config.dart` (the Phase 0 output Discovery §3a defers to here). Juice kept minimal (a tap flash + one sound) — just enough to judge feel.
- **Owns:** flutter-developer + **player-reviewer** (the decisive voice on this gate). game-ux-designer tunes visual feedback timing. tester runs it across ≥2 real Android devices/refresh rates to confirm the band values hold, not just one device.
- **GATE 1 — the explicit decision point (One-Pager):** *Does a stranger replay unprompted?* Put it in real hands.
  - **< kill signal / feels random:** stop and rethink the tap before any content is built. Do not proceed to Phase 3.
  - **feels skillful → continue.** Lock the tuned ms values.
  - Gate is early by design so slippage is visible with room to react (One-Pager risk #2). Budget: this gate may consume extra days — that is expected and comes out of buffer, not by cutting later phases.

### Days 6–10 — Three outcomes + cards + share + daily streak
- **Build:** `outcome_resolver.dart` (all three: Death, Survived/Rebirth, Eternal Human, per Discovery §3 locked rules incl. `life = max(0, life − penalty)` clamp); `card_content_source.dart` + `bundled_card_source.dart` reading `assets/cards.json`; `card_picker.dart`; `card_template.dart` (the one widget); `card_capture.dart` + `share_service.dart`; `daily_streak/`; `hive_profile_repository.dart` with run + lifetime loss counters and seen-card set. "After N deaths" rendered on every card.
- **Owns:** flutter-developer (outcome system, share pipeline, persistence, streak). game-ux-designer (Outcome screen layout, card template visual design, share-CTA placement, streak surfacing). **Content authoring in parallel** (contracted copywriter/artist per One-Pager risk #4): 30–50 death lines + small Survived/Eternal pools + few art variants into `cards.json` — off the founder's critical path. tester verifies outcome-resolver truth table + share produces a valid PNG on device.
- **Done when:** a full loop plays end to end on device — tap → outcome → card with loss count → share sheet opens with the rendered image → replay; streak increments across days; all three outcomes are reachable and correct; card variety visible across runs.

### Days 11–13 — Interstitial + analytics + polish pass
- **Build:** `ad_service.dart` (AdMob interstitial, frequency cap, preload-behind-card, hard placement rules from §1.7); `analytics_service.dart` + `analytics_events.dart` wired to the D1 event set; a focused polish/juice pass (feedback, sound, haptics) — capped, no rich animations.
- **Owns:** flutter-developer (ads + analytics wiring). **backend-engineer** (Firebase project setup, Analytics config, verifying D1-retention + secondary events land correctly in the console; confirms the `CardContentSource` seam is ready for Remote Config in v1.1 but does **not** build RC now). game-ux-designer directs the polish pass against feel, not decoration. code-reviewer audits ad placement rules (never over play surface / never over the death card).
- **Done when:** interstitial shows only on run→run transition, after the card, respecting the cap, with the next run preloaded; D1-retention and secondary events verified arriving in Firebase; polish pass merged without regressing tap latency.

### Days 14–16 — Real-device QA + build + store listing/assets
- **Build:** release build config, app icon, Play Store listing copy, screenshots, feature graphic, privacy policy (ads + analytics data disclosure), Play **Data Safety** form, content rating. Ad IDs/consent (UMP) handling for AdMob.
- **Owns:** tester (full real-device QA pass: outcomes, share, ad cap, streak-across-day-boundary, offline behavior, cold-start clock init). **play-store-specialist** (listing + Data Safety + policy compliance review — ads/analytics disclosures, families/ads policy). game-ux-designer (store creative assets). flutter-developer (release build, consent flow).
- **Done when:** a signed release build passes QA offline and online; the Play listing + Data Safety + rating are complete and pass the play-store-specialist's compliance review; no P0/P1 bugs open.

### Days 17–20 — Store submission + review buffer + **GATE 2 (live)**
- **Build:** submit to Play Store (internal → closed/production track as chosen). Fix any review kickbacks. This window is buffer for Play review, which is faster/more predictable than Apple — the reason Android is first (One-Pager risk #1).
- **Owns:** play-store-specialist (submission + any review-response). flutter-developer (hotfix on kickback). tester (verify the exact submitted build).
- **GATE 2:** **live on Play Store.** Then start watching D1 retention — the sole launch success metric (Floor <10% = kill signal, 15–25% OK, >30% strong).
- **iOS follow:** after Android is live and stable, flip the build target and submit via **app-store-specialist** — a fast-follow, not part of the 20-day box.

## 4. Scope guard — what is explicitly OUT of this launch

Restated from the One-Pager so it cannot silently creep back into architecture. The governing test: *if a feature does not (a) help answer "does the tap feel good / do they come back D1" or (b) move D1 retention, it is out.* None of the below are designed for, stubbed as UI, or partially wired in v1 — except the two named interface seams (§1.6, §1.7) that cost one file each and carry no runtime scope.

- **The full 1000-card library.** v1 ships **30–50 cards, hard cap.** The rest grow post-launch via the template engine + Remote Config — no app update needed. The `card_template.dart` + `cards.json` design makes this a data expansion, not a code change.
- **Banner ads, rewarded ads, IAP, cosmetics.** Only **one** frequency-capped interstitial ships. `AdService` exposes only `maybeShowInterstitial()`.
- **Global leaderboards, Remote Config, accounts, any custom backend.** Firebase is **Analytics-only** for launch (§1.6).
- **Adaptive difficulty tightening.** Ship **fixed** tolerance bands. The adaptive `k` coefficient is scaffolded in `timing_config.dart` but **disabled**; enabling it is a later, retention-data-driven tuning task.
- **Rich per-death animations.** Templated text + a few reusable static art variants only. No bespoke animation per outcome.
- **Onboarding polish, settings depth, themes.** Minimal-to-none for launch.

Writing down what we are **not** building is the primary deadline protector. Any request to add one of these before Gate 2 is out of scope by default and must be re-argued against the governing test above.
