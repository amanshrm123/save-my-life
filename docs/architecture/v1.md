# Stay Alive — Architecture v1

**Scope:** First launch & onboarding only (mockup Section 1, screens 1.1–1.5).
**Project:** `timing_tap` · package `com.timingtap.timing_tap` · dev targets Android + web (no iOS toolchain yet).
**Status:** First feature into a bare `flutter create` scaffold. This doc also makes the foundational calls (state, persistence, routing, theme, module layout) that later features build on.

This is a genuine v1 — no continuity with any prior/discarded architecture is assumed.

---

## 0. What this feature is

A one-time, linear flow shown on the very first launch:

```
1.1 Splash        brand mark + preload bar
1.2 Teach card 1  "Tap on the number"      (dots 1/3, "Next")
1.3 Teach card 2  "Mind your life"         (dots 2/3, "Next")
1.4 Teach card 3  "Three ways it ends"     (dots 3/3, "Got it")
1.5 Name capture  text input, 12-char cap  ("Start playing" primary / "Skip for now" secondary)
        │
        ▼
  <placeholder next screen>   (Play Loop is a separate future feature; not built here)
```

On every subsequent launch the flow is skipped: splash → straight to the placeholder next screen.

---

## 1. State management — decision: **Riverpod** (`flutter_riverpod`), used sparingly

**Recommendation:** adopt `flutter_riverpod` now as the app-wide foundation, but keep the onboarding flow's *ephemeral* UI state (which page is showing, the text in the name field) local to the widget via `PageController` / `TextEditingController`. Only the **persisted, cross-feature** state (the player profile + onboarding-complete flag) goes into a provider.

**Why Riverpod over the alternatives:**
- **vs plain StatefulWidget/InheritedWidget:** onboarding *alone* would be fine with plain widgets. But this is the first feature, and the profile it produces (name, onboarding flag, later: stats, streak, settings, cosmetics) is read by nearly every future screen (countdown "Hey Aman", outcome cards, settings, home). That is exactly the shared-read-many-writers-few shape Riverpod handles cleanly, with testable providers and no `BuildContext` plumbing. Choosing it now avoids a disruptive retrofit at feature 2.
- **vs Provider:** Riverpod removes the `BuildContext` dependency for reads, is compile-safe, and its `AsyncNotifier` maps directly onto "load profile from SharedPreferences (async), then serve it synchronously." Strictly better for this use.
- **vs Bloc:** too much ceremony for a game this size; event/state classes for a 2-field profile are overkill.

**Fit with the RAM-resident convention:** Riverpod holds the single authoritative copy of the profile **in memory**. SharedPreferences is a *write-through durability backup*, not the runtime source of truth — the app reads prefs exactly once at startup, then serves everything from RAM.

**Do NOT** push `PageController.page` or the name text into providers. That would rebuild the world on every keystroke/swipe and complicate disposal. Ephemeral UI state stays in the `State` object.

## 2. Navigation — decision: **Navigator 1.0, no routing package yet**

**Recommendation:** do not add `go_router` (or any routing package) for v1. Use the built-in `Navigator` with a tiny set of route-name constants.

- The flow is strictly linear with no deep links, no tabs, no URL requirements (web target aside — see flag). Retrofitting `go_router` later, when Home/Settings/deep-share-links arrive, is a cheap, additive change. Adding it now is speculative complexity for features that do not exist.

### The teach cards are ONE screen with a PageView, not three routes

The mockup shows dot indicators (1/3 → 2/3 → 3/3), which means swipeable paging. Three separate `Navigator.push` routes cannot share a swipe gesture or a dot indicator cleanly, and would multiply lifecycle/disposal surface.

**Decision:** a single `OnboardingScreen` hosts one `PageController` driving a `PageView` of **4 pages**:

| page index | content        | dots shown | forward action |
|-----------|----------------|------------|----------------|
| 0 | Teach card 1 | 1/3 | swipe or "Next" |
| 1 | Teach card 2 | 2/3 | swipe or "Next" |
| 2 | Teach card 3 | 3/3 | swipe or "Got it" |
| 3 | Name capture | none (mockup 1.5 has no dots) | "Start playing" / "Skip for now" |

Rationale for folding name capture into the same PageView rather than a pushed route:
- One `PageController` to create/dispose — smaller memory-safety surface (see §8).
- Back-swipe from name capture returns naturally to card 3 with no navigator bookkeeping.
- The dots widget simply renders nothing on page 3.

Forward-swipe *into* the name page is allowed; the terminal actions (Start/Skip) live only on that page as buttons.

### Route map

```
Splash ('/')  ──(onboardingComplete == false)──▶  OnboardingScreen  ──(complete)──▶  PlaceholderHomeScreen
      └────────(onboardingComplete == true)──────────────────────────────────────────▶  PlaceholderHomeScreen
```

- `/` = `SplashScreen` is the app's initial route and the only place the branch decision is made.
- Splash → destination uses `Navigator.pushReplacement` (splash must not be back-navigable).
- Onboarding → placeholder uses `Navigator.pushReplacement` (onboarding must not be back-navigable once complete).

Route-name constants live in `core/routing/app_routes.dart` even though we use imperative pushes — cheap, and it seeds the eventual `go_router` migration.

## 3. "Shown once" persistence — decision: **`shared_preferences`**

Add `shared_preferences`. It is the right tool for a handful of scalar flags/strings; no need for `sqflite`/`hive`/`isar` until there is relational or list data (stats history, card collection — all deferred).

**Keys (centralised in `core/persistence/preferences_keys.dart`):**

| key | type | default | meaning |
|-----|------|---------|---------|
| `schema_version` | int | `1` | prefs schema version, for future migrations |
| `onboarding_complete` | bool | `false` | has the one-time flow finished |
| `player_name` | String | `''` (absent) | player's chosen name; empty/absent = anonymous |

**Launch behaviour:**
1. `main()` ensures bindings, constructs the `PreferencesService`, seeds `ProviderScope` overrides, and runs the app.
2. `SplashScreen` reads the profile (via the provider) *once*, holds the brand beat for a minimum display duration, then branches on `onboarding_complete`.
3. `true` → `PlaceholderHomeScreen`. `false` → `OnboardingScreen`.

**When the flag is written:** only at the single terminal moment — when the user taps **Start playing** or **Skip for now**. Never on splash, never per-card, never per-keystroke. This keeps a killed-mid-onboarding app idempotent (see §8).

## 4. Skip semantics — decisions

**"Skip for now" marks onboarding complete (option b).** Skipping proceeds with **no name** (`player_name = ''`) AND sets `onboarding_complete = true`, exactly like "Start playing".

Justification: the section subtitle is *"Shown once… Everything skippable except the splash."* Re-showing the teach cards on the next launch just because the player skipped naming would violate "shown once" and annoy. The no-name path is a first-class supported state — the mockup already ships a name-agnostic outcome-card fallback (3.4). So: skip = anonymous player, flow done.

**"Start playing" with an empty field** is *not* the skip path. The primary button is **disabled** while the name is empty/invalid; "Skip for now" is the explicit anonymous route. This removes ambiguity between "I want no name" and "I forgot to type."

**Re-entry to onboarding later — decision: no.** For v1 the teach cards are truly one-time; there is no re-trigger from Settings or anywhere. What *is* editable later is the **name** (Settings screen 7.1 shows an editable Name row). Therefore the name-capture validation logic must be built as a reusable, screen-independent unit (see §5) so Settings can reuse it without dragging in the teach carousel. (A hidden dev/debug "reset progress" that clears prefs — Settings 7.2/7.3 — will naturally re-trigger onboarding on next launch, but that is a future feature, not part of this task.)

## 5. Name capture logic — decision: pure `NameValidator`

**Where it lives:** `lib/features/onboarding/domain/name_validator.dart` — pure Dart, **no Flutter imports**, unit-testable in isolation, reusable by the future Settings "edit name" flow.

**Signature shape:**
```
NameValidationResult validate(String raw)
  → { bool isValid, String sanitized, NameRejectReason? reason }
```
`NameRejectReason` enum: `tooLong`, `empty`, `illegalChars`, `disallowedWord`.

**Rule set (in order):**
1. **Sanitize:** trim leading/trailing whitespace; collapse internal runs of whitespace to a single space.
2. **Length:** after sanitize, `1 ≤ length ≤ 12`. The `TextField` also hard-caps input at 12 via `maxLength`/`LengthLimitingTextInputFormatter`, but `NameValidator` re-checks so the rule is authoritative and testable independent of the widget. Empty (post-trim) → `empty` (button stays disabled; not an error toast).
3. **Character set:** allow Unicode letters, digits, spaces, a small punctuation set (`- ' _`), and emoji (Unicode emoji/pictographic ranges, including ZWJ sequences so composite emoji don't get split mid-grapheme). Reject other control/formatting characters. **Founder-confirmed:** emoji are allowed in names since they render on shareable outcome cards. Note for implementation: the 12-char cap must be enforced in *grapheme clusters* (`characters` package), not UTF-16 code units, so a single multi-codepoint emoji doesn't silently consume 2-4 of the 12 slots.
4. **Disallowed words (profanity):** name is rendered publicly on shared cards, so a blocklist check is in scope conceptually. **Decision for the first cut:** build the *hook* now — `NameValidator` takes an injected `ProfanityFilter` with a small seed blocklist — so the rejection state (mockup 8.1 "Pick another name") is reachable and testable. Ship only a trivial seed list; a comprehensive/localised list is **deferred** to a later hardening pass.

**Where the rejection UI shows:** inline within the name-capture page (red border + helper text, matching mockup 8.1's copy "That word isn't allowed — it shows on shared cards"). The dedicated full-screen 8.1 treatment is a game-ux-designer detail; functionally it is an inline error state on page 3. Validation runs on submit ("Start playing"); length cap is enforced live by the input formatter.

## 6. Data model — `PlayerProfile`

**Now (v1):**
```
class PlayerProfile {
  final String name;              // '' == anonymous
  final bool onboardingComplete;
  const PlayerProfile({required this.name, required this.onboardingComplete});
  PlayerProfile copyWith({String? name, bool? onboardingComplete});
  bool get isAnonymous => name.isEmpty;
  static const empty = PlayerProfile(name: '', onboardingComplete: false);
}
```
- Immutable, with `copyWith`. Lives in `features/onboarding/domain/player_profile.dart`.
- `name` is non-null `String` (empty = anonymous) rather than `String?` — one fewer null to reason about across every consumer; `isAnonymous` is the semantic check.

**Deferred (do NOT add fields now):** lifetime stats (deaths, survives, eternal count, best life), daily streak, settings toggles (sound/haptics/reminders), cosmetics/skins, per-death collection. These arrive with their own features. The persistence layer is designed so adding them is additive: new typed key + new field + `copyWith`, guarded by `schema_version` for migration.

## 7. Package / module layout

Add to `pubspec.yaml` `dependencies`:
```
flutter_riverpod: ^2.6.1     # (or latest 2.x — resolve via `flutter pub add`)
shared_preferences: ^2.3.2   # (resolve via `flutter pub add`)
characters: ^1.4.1           # grapheme-cluster-aware length checks (emoji names, §5)
```
No routing package. No extra test package — `NameValidator` is pure, and the repository can be tested with the built-in `SharedPreferences.setMockInitialValues`.

**Fonts:** the mockup uses **Fredoka**. **Decision: bundle Fredoka as a local asset font, do NOT use `google_fonts`.** Rationale: the game is offline-first (mockup 8.2 explicitly promises full offline play); `google_fonts` fetches over the network on first use, which is exactly wrong for a first-launch splash with no guaranteed connectivity. Bundling is deterministic and offline-safe. (Font files + `pubspec.yaml` `fonts:` section — see flag; a game-ux-designer/asset step.)

**Folder layout (minimal, lightly layered — do not add folders for features that don't exist):**
```

  app.dart                          # root MaterialApp: theme, initialRoute '/', route table
  core/

    persistence/

      preferences_service.dart      # thin async wrapper over SharedPreferences
    routing/
      app_routes.dart               # route-name string constants
  features/
    onboarding/
      domain/
        player_profile.dart         # immutable model (§6)

      data/
```

**Theme colors to lift from the mockup `:root`** (put in `app_theme.dart`): bg `#c8ecd9`, ink `#1f2a2e`, paper `#fffdf7`, coral `#ff7a59` / `#e5613f`, green `#2fbf71` / `#1f9c58`, red `#f0483e`, gold `#ffc23c`, mute `#7b8a86`, blue `#4a9fd8`. ## 8. Memory-safety review (required before implementation)

The app aims to be RAM-resident; the failure modes here are lifecycle and re-entrancy, not heap size. Each risk + required handling:

1. **App killed mid-onboarding, before the complete flag is written.**
   *Handling:* the flag and name are written **only** at the terminal action (§3). There is no partial/half-written profile at any earlier point — the name lives purely in the `TextEditingController` (RAM) until submit. Result: a kill at any point before Start/Skip simply restarts onboarding cleanly next launch. Idempotent by construction. **Do not** persist the name on each keystroke.

2. **`PageController` / `TextEditingController` disposal.**
   *Handling:* both are created as fields of `_OnboardingScreenState` (in `initState` or as `late final`) and **must** be disposed in `dispose()`. Any splash preload `AnimationController` likewise. Do not create controllers inside `build`.

3. **Re-entrant navigation from double-tapping Start / Skip.**
   *Handling:* guard with a `bool _submitting` flag in the state; the first tap sets it and ignores subsequent taps. Because completion does an async prefs write then `pushReplacement`, a double tap could otherwise push the placeholder twice.

4. **`BuildContext` used across an async gap.**
   *Handling:* after `await repository.complete...()`, check `if (!mounted) return;` before touching `Navigator`/`context`. Same discipline for any `ref` usage after an await. This covers "user backgrounds/kills the app while the prefs write is in flight."

5. **Double/over-fast "Next" taps over-advancing the PageView.**
   *Handling:* compute the target page from the current page and clamp to `[0, 3]`; ignore a "Next" if a page animation is already in flight (or simply drive off `controller.page.round()`). Prevents skipping card 2 or landing past the name page.

6. **Splash timer firing after the screen is gone.**
   *Handling:* implement the minimum brand-beat as an `await Future.delayed(...)` followed by `if (!mounted) return;` before navigating, rather than a bare `Timer` that captures `context`. If the user backgrounds during splash, the guard prevents navigating a dead tree.

7. **SharedPreferences read failure / first-launch absent keys.**
   *Handling:* the repository returns defaults (`onboarding_complete=false`, `name=''`) for absent/failed reads and never throws into the UI. First launch is just "everything at default."

8. **`TextEditingController` listener leak.**
   *Handling:* if a listener is attached to drive the enable/disable of "Start playing", remove it in `dispose()` (or read the controller directly in a local rebuild scope). Prefer no long-lived listener — a `ValueListenableBuilder` around the controller scopes the rebuild to the button and needs no manual teardown.

9. **PageView children kept alive unnecessarily.**
   *Handling:* teach cards are cheap; do **not** add `AutomaticKeepAliveClientMixin`. Let off-screen pages drop. Nothing here needs to survive being scrolled away.

10. **Android hardware back during onboarding.**
    *Handling:* wrap onboarding in `PopScope`; back on page > 0 animates to the previous page and consumes the pop; back on page 0 allows normal app-exit. (Exact UX — whether page 0 back exits the app or is a no-op — is a flag below.)
