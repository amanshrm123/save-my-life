# Architecture v3

*Living document. Current agreed architecture for the Timing-Tap launch. Per the versioning convention, `vN.md` files are **never edited in place** — this file supersedes `docs/architecture/v2.md` (which stays as the historical record of the scope-expansion cut). It reconciles the founder's five Play-Loop change requests into the existing plan. Source of truth for design: `docs/discovery/TimingTap_Discovery_v1.md` (the ground-truth timing/outcome spec — corrected 2026-07-22 for item 4, see §4) and the play-loop design docs (`docs/design/play-loop-v2.md`, the current pixel-fidelity pass). The next agreed revision lands as `v4.md`.*

## 0. What changed from v2, and why

v2 expanded launch scope to the full screen library and set the 28–32 day plan. **v3 does not touch that plan's shape.** It reconciles five founder requests against the current Play-Loop build (branch `phase2-play-loop`, on top of the v2 pixel-fidelity reskin). Three of the five are genuine architecture decisions, not polish:

1. **Persisted, incrementing Run count with real cycle-end detection.** Pulls a *minimal, honest slice* of the deferred outcome system (Days 6–11) forward: end-of-run detection (Death only), an incrementing counter persisted via the existing `ProfileRepository`, and a restart into a fresh cycle. **Explicitly deferred within this ask:** the "life saved"/Survived win condition — see §3, and the founder-confirmation flag in §9.
2. **Life starts at 100%.** A one-constant change with test fallout (§5).
3. **The number (numplate) becomes a tap target.** A real ergonomics/measurement decision that reverses the fidelity pass's tap-target call a *second* time — reconciled in §6 with a recommendation and a founder flag.
4. **Hit/Miss life-deltas rolled randomly within ranges** (not fixed constants). Restores the discovery doc's original intent; requires a purity-preserving change to `resolve()` and a new displayed field. **Explicitly distinguished from the banned adaptive-tightening mechanic** — §4.
5. **The result indicator animates, flying from the tap button up to the numplate.** Lifts the Gate-1 `AnimationController` ban for this one element only, under a controlled spec (§7).

**What this does NOT change (carried forward from v1/v2, not re-argued):** the monotonic-clock-only rule; timestamp-in-`onPointerDown`; `Listener`-only tap capture (never `GestureDetector`/`InkWell`/`StickerButton`); `resolve()` stays pure; flash fires strictly *after* `registerTap()` resolves; Riverpod/Hive/AdMob/Analytics stack; the 30–50 card cap and the full scope guard (v2 §6), including the still-banned adaptive difficulty tightening and the deferred death-collection gallery.

This is a **reconciliation, not a rewrite.**

## 3. Item 1 — cycle-end detection, persisted Run count, restart

### 3.1 What "cycle end" means for THIS pass — the call

**Decision: a cycle ends on Death, and Death only. Death = life reaches exactly `0%`.** No other end condition is implemented in this pass.

**Why "life saved"/Survived is deferred, not built as a half-version:**
- In the locked design (discovery §3), "life saved" is a *specific* mechanic — **Survived / Rebirth**: while in the *final band* (a state where the next miss is fatal), the player lands a clutch on-point that ends the run instantly as a win. It is **not** "reach 100% life." Reaching 100% just clamps (v1/v2 behavior) and the run continues.
- None of the machinery for that exists: there is no *final-band* concept in code, no `outcome_resolver.dart`, no Eternal-Human first-3-presses tracking. Those are the Days 6–11 outcome system.
- Inventing an ad-hoc "reach 100% = saved" or "N perfects = saved" rule *this pass* would ship a mechanic the design explicitly does **not** have, that would then have to be ripped out and replaced at Days 6–11. That is exactly the overbuild the scope guard exists to prevent.
- Death, by contrast, is already fully specified and needs no invented rules: it is simply `life == 0`. It is the honest minimal slice that makes the Run counter real.

**So: the Run/Deaths counter increments only on Death in this pass.** When the full outcome system lands (Days 6–11), Survived and Eternal Human become additional cycle-end triggers that also increment the run counter and route to their own cards; the persistence field and the restart plumbing built here are forward-compatible with that and do not need to change.

> **Founder-confirmation flag (see §9):** your words were "once the life is saved *or* death takes place." This pass implements only the Death half and defers the "life saved" half as still-out-of-scope outcome-system work. Confirm this is acceptable, or that you want the full Survived condition pulled forward too (which materially enlarges this pass — it drags in the final-band concept and `outcome_resolver.dart`).

### 3.2 Run count semantics — one persisted integer

**Persist exactly one new integer: `deathCount` (lifetime deaths).** Both chips derive from it, so no second field is needed:

- **Deaths chip** = `deathCount`.
- **Run chip** = `deathCount + 1` (the attempt you are currently playing — you're on Run 1 with 0 deaths, Run 2 after your first death, etc.).

This is the cheapest correct model. It replaces the hardcoded `'Run'/'1'` + `'Deaths'/'0'` literals that `play-loop-v2.md` §2.1 deliberately stubbed — that doc's stated condition for replacing them ("once `outcome_resolver.dart` + lifetime counters exist") is now partially met by this pass's death-detection + persistence, so the chips become real here. The chip *widget shell* (`_Chip`) does not change; only its values become provider-backed.

### 3.3 State machine change — add `RunPhase.dead`

```
enum RunPhase { countdown, playing, dead }   // + dead
```

`RunState` gains:
- `int deathCount` — lifetime deaths, initialized from the repository in `build()`, incremented in-memory on death (so the chip updates immediately without re-reading Hive).

`RunController` changes:
- **`build()`** reads the resolved `ProfileRepository` (see §3.4) and seeds `deathCount` from `repo.deathCount`. Life seeds at `100.0` (item 2).
- **`registerTap(pressMicros)`** — after computing `newLifePct`, if `newLifePct <= TimingConfig.minLifePct` (i.e. `0`), it must:
  1. set `phase = RunPhase.dead`,
  2. increment `deathCount` in-memory,
  3. fire-and-forget `repo.incrementDeathCount()` (async; do not `await` in the tap path),
  4. still record `lastBand`/`lastDeltaMs`/`lastLifeDelta` for the flash (the fatal tap still shows its Miss result),
  5. **not** roll a new target (the run is over).
- **`registerTap` must be a no-op when `phase != RunPhase.playing`** — a tap during `dead` (or `countdown`) must not score. This also fixes the current implicit assumption that taps only ever arrive during play.
- **New `startNewCycle()`** — resets `lifePct = 100.0`, `phase = RunPhase.countdown` (so the 3-2-1 replays), rolls a fresh target, and clears `lastBand`/`lastDeltaMs`/`lastLifeDelta`. `deathCount` is **not** reset (it's lifetime). This is what "fetched when the next cycle starts" resolves to: the incremented count is already in `RunState.deathCount`, and the countdown → playing transition uses `beginPlaying()` exactly as today.

### 3.4 Persistence — extend `ProfileRepository`, same single Hive box (no new store)

Per v2 §3.4's standing decision (extend the one repository, never add a second store):

`ProfileRepository` (interface) gains:
```dart
int get deathCount;                    // defaults to 0 on a fresh install
Future<void> incrementDeathCount();    // read-modify-write on the same box
```

`HiveProfileRepository` adds `static const _keyDeathCount = 'deathCount'`, reads `(_box.get(_keyDeathCount) as int?) ?? 0`, and `incrementDeathCount()` puts `deathCount + 1`. `FakeProfileRepository` (test seam) mirrors it with an in-memory int + a call counter (matching the existing `markOnboardingCompleteCallCount` pattern) so tests can assert persistence happened exactly once per death.

**How `RunController` gets the repository (the one real wrinkle):** `profileRepositoryProvider` is a `FutureProvider`. `RunController` is a synchronous `Notifier`. This is safe because **`PlayScreen`/`RunController` are only ever reached after `SplashScreen` has already awaited that provider** — the same guarantee `CountdownView` already relies on for `name` (`countdown_view.dart` build()). So `RunController.build()` reads `ref.read(profileRepositoryProvider).requireValue`. Document this precondition in the controller; if a future entry point could reach Play before the repo resolves, this must be revisited (it can't today).

### 3.5 The minimal death state — placeholder, NOT the outcome card

When `phase == RunPhase.dead`, `PlayScreen` renders a **minimal placeholder** — this is explicitly *not* the Days 6–11 outcome card (no death-line pool, no art, no share). The honest minimal version: a simple centered overlay reading roughly "You died" + the death count + a single **"Play again"** tap target that calls `startNewCycle()`.

- **Recommendation: explicit tap-to-restart, not auto-restart.** Auto-restarting into a countdown involuntarily feels like the game grabbing control back from the player; and the eventual outcome card *is* a tap-to-continue surface, so a tap-to-restart now is forward-compatible and won't be thrown away. This placeholder occupies the same conceptual slot the outcome card will later fill.
- **Flag for `game-ux-designer`:** this is a deliberately un-designed placeholder. Do not invest polish here — the real outcome card (Days 6–11) replaces it wholesale. Keep it legible and on-brand (paper/ink), nothing more.

## 4. Item 4 — random life-delta within band ranges

### 4.1 The ranges — the call

| Band | Timing window | Life delta | Fixed / rolled |
|---|---|---|---|
| **Perfect** | ≤ ±30 ms | **+3.0%** | **Fixed** |
| **On-point (Hit)** | ≤ ±80 ms | **+2.0% to +3.0%** | Rolled per tap |
| **Miss** | > ±80 ms | **−5.0% to −3.0%** | Rolled per tap |

**Perfect stays fixed at +3%.** The discovery doc never gave Perfect a range; it is the elite tolerance tier and must remain the *guaranteed reward ceiling*. If Perfect were also rolled, a low Perfect roll could land below a lucky On-point roll — inverting the tier ordering (tighter timing rewarded less than looser timing), which is incoherent. Fixed Perfect = "nail the timing, get the guaranteed best." On-point = "close enough, variable reward." This is a clean, defensible design and matches the corrected discovery §3a.

**Step granularity — the call: whole-integer steps, uniform.** On-point rolls uniformly over `{+2, +3}`; Miss rolls uniformly over `{−3, −4, −5}`. Rationale:
- **Honest display.** The life bar and the flash pill can show exact integers ("MISS −5%", "ON POINT +2%") that *reconcile with the bar movement*. Continuous rolls (e.g. −4.37%) would force either an ugly decimal or a rounded display that no longer matches the real accumulated life — a subtle dishonesty a counting player notices.
- **Real variety with clean math.** Miss now has three distinct outcomes; On-point two. That is exactly the "not permanent / random" the founder asked for, without introducing float drift into the life total.
- Perfect's `{+3}` is a degenerate one-value "range" — i.e. fixed — which keeps the code path uniform (every band is `pick-from-a-set`) even though only two bands actually vary.

### 4.2 Where the randomness lives — keep `resolve()` pure

`resolve()` must stay a **pure, deterministic function** (v1 §1.2, discovery §3a "measurement correctness"; it has full boundary-test coverage that depends on determinism). So the random source does **not** go inside it. Instead:

- `resolve()` gains one parameter: `required double lifeRoll` — a value in `[0, 1)`. The function stays pure: same inputs (including `lifeRoll`) → same output.
- The band decision is unchanged and still purely timing-driven. Only the *magnitude* now maps through the roll via a small pure helper:
  ```dart
  double lifeDeltaFor(TimingBand band, double lifeRoll) // pure, unit-tested
  ```
  Perfect → `perfectLifeDelta` (ignores roll). On-point → pick from `{2, 3}` by `lifeRoll`. Miss → pick from `{−3, −4, −5}` by `lifeRoll`.
- **`RunController` owns the randomness.** It already holds a `Random _random`; it passes `_random.nextDouble()` as `lifeRoll` into `resolve()` on each `registerTap`. This keeps *all* nondeterminism in the controller (which already rolls target durations) and leaves the engine deterministic and headlessly testable — tests pass an explicit `lifeRoll` (e.g. `0.0` → floor, `0.999` → ceiling) to assert exact band-magnitude mapping.

### 4.3 New displayed field — `RunState.lastLifeDelta`

Because the delta is now variable, the flash pill can no longer read a constant from `TimingConfig`. Today `_FlashPill._copy` reads `TimingConfig.perfectLifeDelta`/`onPointLifeDelta`/`missLifeDelta` — with ranges, those constants no longer describe what *this* tap actually did.

- Add `double? lastLifeDelta` to `RunState`, set alongside `lastBand`/`lastDeltaMs` in `registerTap`.
- `_FlashPill` renders the **actual** value: `"ON POINT ${_formatSignedLifeDelta(runState.lastLifeDelta)}%"`, etc. (`_formatSignedLifeDelta` already handles the sign/formatting.)
- **The two static legend pills** (`_LegendPill`, "Hit …%" / "Miss …%") can no longer show a single number honestly. **Call: show the range** — `"Hit +2–3%"`, `"Miss −5 to −3%"` (or `"Miss −3–5%"`). Sourced from the new range constants, not hardcoded digits (same correctness-over-cosmetics rule as v2 §2.4/§3.4). `game-ux-designer` picks the exact compact string; `flutter-developer` wires it from `TimingConfig`.

### 4.4 `TimingConfig` changes

Replace the two fixed miss/on-point constants with range bounds; keep Perfect fixed:
```dart
static const double perfectLifeDelta = 3.0;      // unchanged, fixed
static const double onPointLifeDeltaMin = 2.0;    // +NEW
static const double onPointLifeDeltaMax = 3.0;    // +NEW
static const double missLifeDeltaMin = -5.0;      // +NEW (most negative)
static const double missLifeDeltaMax = -3.0;      // +NEW (least negative)
// remove: onPointLifeDelta = 2.0; missLifeDelta = -4.0;
```
The stale `missLifeDelta = -4.0` comment (which itself flagged this divergence) is resolved by this change. `adaptiveK` stays `0.0`, untouched.

### 4.5 The non-negotiable distinction (state it, so no one confuses it with the ban)

**Rolling the life-delta magnitude within a band ≠ adaptive difficulty tightening (still banned).**
- **Banned mechanic (adaptive tightening):** narrows the *time tolerance window* (`HIT_MS`) as life% climbs, via the `k` coefficient — changes *which band a tap lands in*. Still off (`adaptiveK = 0.0`).
- **This item (magnitude roll):** the band is *already resolved* by fixed timing thresholds; only the reward/penalty *size* within that band varies, and the roll **does not read life%**. It never touches `HIT_MS`/`PERFECT_MS`/`adaptiveK`.

`code-reviewer` should assert: `lifeDeltaFor`/`resolve` take `lifeRoll` but never read `lifePct` for the magnitude; `adaptiveK` remains `0.0` and unread.

## 5. Item 2 — life starts at 100%, and its test fallout

`run_controller.dart`: `_startingLifePct` `50.0` → `100.0`. `build()`'s `lifePct` and `startNewCycle()`'s reset both use it.

**This breaks several existing assertions — flag for `flutter-developer`/`tester` (these MUST be updated in the same PR, or the suite goes red):**

`test/features/run/run_controller_test.dart`:
- `'starts at 50% life…'` → assert `100.0`.
- The three single-tap magnitude tests (`Perfect …53.0`, `On-point …52.0`, `Miss …46.0`) are **doubly invalidated**: (a) from a 100 start, Perfect/On-point immediately clamp to 100 (unobservable), and (b) deltas are now *ranged* (item 4), so exact end-values are wrong. Rewrite: drive life down first to create headroom, and assert band + that `lifePct` moved by an amount *within the band's range* (e.g. Miss → `lifePct ∈ [95, 97]`), not an exact number. Prefer overriding `lifeRoll` via an injected `Random` (or testing `resolve()` directly with explicit `lifeRoll`) for exact-value assertions.
- Accumulation/clamp tests that assume a 50 start and −4 flat (`'50 -> 53 -> 56 -> 59'`, `'exactly 0.0 from exactly 100.0 after exactly 25 Miss taps'`, the clamp-at-0 loops) — rewrite for 100 start and ranged Miss. Note the "exactly 25 taps" test is invalid once Miss is ranged; replace with "repeated Misses eventually reach 0 and trigger death" (which now also asserts item 1's `phase == dead`).
- The clamp-at-0 tests that currently keep tapping *after* life hits 0 must change: a run now **ends** at 0 (`phase == dead`), and further `registerTap` calls are **no-ops**. Rewrite to assert death-on-zero + no-op-after-death, not "life stays 0 under more Miss taps while still playing."

`test/features/timing_engine/timing_engine_test.dart`:
- `resolve()` calls gain the new `lifeRoll` param. Boundary/band tests pass a fixed `lifeRoll` (e.g. `0.0`). Assertions of `result.lifeDelta == TimingConfig.onPointLifeDelta`/`missLifeDelta` change: Perfect still `== perfectLifeDelta`; On-point/Miss assert against the rolled value for the given `lifeRoll` (e.g. `lifeRoll 0.0` → min-magnitude). Add a focused `lifeDeltaFor` test group (roll → value mapping per band, Perfect ignores roll).

**New tests to add:** death-on-zero sets `phase == dead` + increments `deathCount` + calls `incrementDeathCount()` exactly once; `registerTap` is a no-op when `phase != playing`; `startNewCycle()` resets life to 100/phase to countdown/clears last-tap fields but preserves `deathCount`; `build()` seeds `deathCount` from the repository. `RunController` tests will now need a `profileRepositoryProvider` override with a `FakeProfileRepository` (they currently override only `clockProvider`).

## 6. Item 3 — the number as a tap target (the ergonomics decision)

### 6.1 The tension, stated honestly

The core game measures **timing precision**, and the discovery doc's "consistent latency path" rule means the measurement should carry as little *non-timing* noise as possible. **Spatial aiming is non-timing noise.** The original skeleton spec deliberately made the tap zone large/full-size precisely so a player never *misses spatially* — the only skill measured is *when* you tap, not *where*. `play-loop-v2.md` §2.2 already reversed that once, shrinking the tap zone to an 88dp button for pixel fidelity. Item 3 pushes toward an even smaller target — the ~120×70dp numplate — which would reintroduce spatial-miss noise into a timing game. Taken literally (numplate-sized hit area), that is a genuine *measurement* regression, not just an ergonomic one.

But the founder's underlying intent is legitimate and is about **affordance/clarity**: "Tap at 16.00" should feel like you tap the number. That's a good instinct — the current disconnect (label says "Tap at [number]" but the button is elsewhere) is genuinely confusing.

### 6.2 The recommendation

**Make the numplate a real tap target, but give it a generous, forgiving hit area — the number is the visual anchor, the tappable region is larger than the number's box — and keep the bottom TAP button as a second valid tap target.**

Concretely:
- Wrap the center zone's numplate (and comfortable padding around it) in a **second `TapSurface`** (`Listener`, `HitTestBehavior.opaque`) that calls the **same** `onTapMicros` handler as the bottom button. The effective hit area is the padded region around the number (target well above the 48dp minimum, closer to the numplate + surrounding whitespace), not the literal glyph bounds — so the number *looks* like the target while the timing measurement stays spatially forgiving.
- Keep the existing bottom 88dp `TapSurface` button as-is. It remains the ergonomic one-handed thumb target; removing it would hurt reachability and undo v2's fidelity work.
- **Both `TapSurface`s share one `onTapMicros` → `registerTap` path.** Each captures its timestamp in its own `onPointerDown` (the hard rule is per-Listener and unchanged). They never spatially overlap, so a single physical tap fires exactly one of them — no double-scoring risk from one touch.

**Why not the alternatives:**
- *Numplate-only, literally number-sized:* rejected — reintroduces spatial-miss noise into a timing measurement; a mis-aimed tap would score as a real (probably Miss) result, which is unfair and corrupts the core metric.
- *Move the Listener to the numplate and delete the bottom button:* rejected — loses one-handed reach and discards v2's fidelity pass; also a small centered target is harder under time pressure.
- *Two independent scoring surfaces feels redundant:* acknowledged, but they share one handler and one code path, so there's no logic duplication — just two hit regions for one action, which is common and fine.

### 6.3 Flag for founder (§9)

Confirm you're happy with: (a) **both** the number and the bottom button being pressable (recommended), versus number-only; and (b) the number's tappable region being *deliberately larger than the number itself* (looks like you tap the number, but the hit area is forgiving) — this is the honest way to satisfy the affordance without making a timing game depend on aiming accuracy. If you specifically want the bottom button *removed*, say so — I recommend against it, but it's a clean change if you insist.

## 7. Item 5 — the result indicator flies from the TAP button to the number

### 7.1 What changes, and the ban it lifts

Today `_FlashPill` appears statically via `Positioned(top: 0)` in the center-zone `Stack` and is cleared by a 120ms `Timer`. The founder wants it to **originate at the tap button and travel up to the numplate/"Tap at" area**, per the attached UI/UX.

This requires motion over time — an `AnimationController`. The Gate-1 spec banned `AnimationController`/curve-tuning as premature juice. **v3 lifts that ban for this single element only** (the flying result pill). Everything else stays animation-free; the tap-capture path in particular gains **no** animation and no ticker.

### 7.2 The non-negotiable that does NOT change

**The flash still fires strictly *after* `registerTap()` resolves.** The animation is *triggered from inside `onTapMicros`, after* `ref.read(runControllerProvider).lastBand` is read — i.e. downstream of resolution, exactly where the flash-band set happens today. The `AnimationController.forward(from: 0)` call replaces the `tapFlashBandProvider` set + `_pendingFlashClearTimer` schedule; the ordering guarantee is identical. It is **never** started in `TapSurface.onPointerDown` or inside `resolve()`. `code-reviewer` audits this the same way it audits the current flash rule.

### 7.3 Technical approach (architecture — `game-ux-designer` fills exact visual values)

- **Overlay layer.** Wrap the `RunPhase.playing` body in a top-level `Stack`: layer 0 is the existing `Column`; layer 1 is the animated pill, positioned absolutely so it can travel *across* the Column's regions (the numplate and the button live in different parts of the Column, so the pill cannot animate within the center-zone `Stack` alone).
- **Anchors via `GlobalKey`.** Put a `GlobalKey` on the numplate and on the tap button. After `registerTap` resolves, read each key's `RenderBox` global position (converted to the overlay `Stack`'s local coordinates) to get `start` (tap-button center) and `end` (numplate center). Using real render positions keeps the flight correct across screen sizes/orientations rather than hardcoding offsets.
- **The animation.** A single `AnimationController` (in a `StatefulWidget` — either promote `PlayScreen` to stateful with `SingleTickerProviderStateMixin`, or introduce a small `_FlashFlightLayer` stateful child that owns the controller). Drive:
  - a `Tween<Offset>(begin: start, end: end)` (position),
  - an opacity curve (fade in fast at launch, hold, fade out at/after arrival),
  - optional slight scale — `game-ux-designer`'s call.
- **Timing (starting recommendation, designer tunes):** ~280ms travel, `Curves.easeOut`, then a ~120–150ms dwell at the numplate before clearing — total ~400–450ms. This is deliberately short: it's feedback, not a cutscene, and must never feel like it delays the next tap.
- **Re-tap handling.** A rapid second tap restarts the flight from the new result (`controller.forward(from: 0)` with recomputed band/positions), mirroring today's `_pendingFlashClearTimer?.cancel()` pattern — never queue or block. The pill reflects the latest tap only.
- **Coexistence with the button color-wash.** The existing `_TapZone` fill wash (coral → green/red on tap) **stays** — it reads as the button "launching" the pill, which is coherent with the pill originating there. No conflict.

### 7.4 Hand-off boundary

- **`game-ux-designer`:** exact duration, curve, opacity/scale keyframes, dwell time, pill size/shadow during flight, and whether the pill fades or pops at the numplate. Owns the *feel* of this motion (this is the founder's "juice" ask — treat it as such).
- **`flutter-developer`:** the `Stack` overlay, the two `GlobalKey`s + `RenderBox` position math, the `AnimationController`/`Tween` wiring, and the strict "start only after `registerTap` returns" ordering. Builds from §7.3 + the designer's values.

### 7.5 Flag for founder / designer (§9)

The "attached UI/UX" referenced in the request isn't in the repo I can see. §7.3 is the architecture (how it moves, safely); the *exact* visual choreography must come from that attachment via `game-ux-designer`. If the attachment implies something structurally different from "one pill travels button→number" (e.g. a trail, particles, multiple elements), that changes the widget structure and should be re-checked against this spec before build.
