# Stay Alive — Architecture v3

**Scope:** the remaining screen inventory — Outcome Cards (mockup §3), Sharing (§4), Ads (§5), Home & Progression (§6), Settings (§7), Edge & Error states (§8) — wired into a single coherent app on top of the merged onboarding (v1) and Play Loop (v2) foundations.
**Builds on:** v1 and v2 (both merged, both stay as-is — this is a new doc, not an edit).
**Project:** `timing_tap` · Android + web dev targets (no iOS toolchain) · `flutter_riverpod ^3.3.2`, `shared_preferences ^2.5.5`, `characters ^1.4.1` already present.

This is a large multi-subsystem pass. It replaces the two placeholder screens (`PlaceholderHomeScreen`, `PlaceholderOutcomeScreen`) with the real Home and real Outcome Cards, and adds five new feature modules. Several parts have **real external dependencies or open-ended content** that I deliberately do not assume through — those are called out in §1 and repeated in the sign-off section.

---

## 0. What is in and out of this pass

**In:** Outcome cards (3.1–3.4) with a seeded flavor-text content pool; sharing (render-to-image + native share sheet); ad *screens/flow* behind a fake ad service; Home hub with daily streak + lifetime stats; the Stats screen; Settings (sound/haptics/name/reminder + legal/reset); daily-reminder notifications as a real subsystem; the in-context notification opt-in (8.4); ad-failed (8.3) handling.

**Out (deferred, with rationale in §1):** any real ad-network SDK/account; the rewarded-ad flow entirely (founder-resolved — it would currently grant nothing real, since cosmetics/skins is also out of scope); the card-collection gallery (6.5, the mockup's own "post-v1 candidate"); the explicit "You're offline" screen (8.2, no network feature exists to fall back from); real legal policy text (§7/§1 item 6).

Screen 8.1 (name rejected) is already delivered — it's the inline rejection state built into onboarding v1 §5 via `NameValidator`; Settings "edit name" reuses the same validator (§7).

## 2. Data model & persistence (reconciled — no duplication)

The single persistence owner stays `PreferencesService`; the single run-completion writer stays **`RunStatsRepository`** (v2). I **extend** both rather than adding a parallel stats store.

### New `shared_preferences` keys (additive — no `kPrefsSchemaVersion` bump; consistent with v2 §6)

| key | type | default | owner |
|-----|------|---------|-------|
| `total_survives` | int | 0 | RunStatsRepository |
| `total_eternal` | int | 0 | RunStatsRepository |
| `best_life_percent` | int | 0 | RunStatsRepository |
| `streak_current` | int | 0 | RunStatsRepository (streak) |
| `streak_best` | int | 0 | RunStatsRepository (streak) |
| `streak_last_play_day` | int | -1 | RunStatsRepository (streak); local epoch-day index, -1 = never |
| `sound_enabled` | bool | true | SettingsRepository |
| `haptics_enabled` | bool | true | SettingsRepository |
| `reminder_enabled` | bool | false | SettingsRepository |
| `reminder_opt_in_shown` | bool | false | SettingsRepository (gates the once-only 8.4 prompt) |

(`total_runs_played`, `total_deaths`, `onboarding_complete`, `player_name`, `schema_version` already exist.)

### Extending `RunStatsRepository` (reconcile, don't duplicate)

`recordRunCompleted({required bool wasDeath})` becomes richer — it must record survives/eternal and best-life, so it takes the whole run result:

```
recordRunCompleted(RunSummary summary)
  runsPlayed++
  switch(summary.outcome): death→deaths++ ; survived→survives++ ; eternal→eternal++
  bestLifePercent = max(bestLifePercent, summary.peakLifePercent)
  // streak handled separately, see registerPlayDay()
```
Read-side getters added: `totalSurvives`, `totalEternal`, `bestLifePercent`, plus the streak triplet. All reads defend against absent/corrupt keys with defaults (v1 §8.7 precedent); all writes swallow their own failures.

### `RunSummary` — closes the v2 gap for the outcome cards

The outcome cards need per-run data the current `RunState` doesn't fully carry. Add to `RunState` (tracked in `RunController.registerStop`): `peakLifePercent` and `minLifePercent`. At run end `RunController` builds:

```
class RunSummary {          // features/play_loop/domain/run_summary.dart
  RunOutcome outcome;
  int runNumber;            // this run's lifetime index
  int lifetimeDeaths;       // deaths total (for "Death #… " context copy)
  int peakLifePercent;      // "Peaked at 61%"
  int minLifePercent;       // "Down to 3%"
  int perfectCount;         // for Eternal "3/3"
  String playerName;        // '' == anonymous → no-name card variant (3.4)
}
```
`RunSummary` is passed to the outcome screen via the navigation builder (same mechanism `PlaceholderOutcomeScreen(outcome)` already uses — a pushed `fadeSlideRoute` with a constructor arg, not the `routes` map).

### Streak model (pure, testable)

```
class DailyStreak { int count; int best; int lastPlayDay; }   // features/progression/domain/streak.dart
```
`StreakCalculator` (pure, no Flutter):
- `int today()` → local calendar epoch-day (`DateTime` truncated to y/m/d, days since epoch, **local** time).
- `StreakResult registerPlay(DailyStreak prev, int today)` → transition ∈ `{firstEver, sameDay, advanced, brokenRestarted}`; updates `count`/`best`/`lastPlayDay`.
- `bool isBrokenAtOpen(DailyStreak s, int today)` → `today - s.lastPlayDay > 1` (used by Home to show 6.3 before the player has played today).

Called from `RunController` at run completion via `RunStatsRepository.registerPlayDay(today)`, which returns the transition so the post-run flow can surface 6.2 when it `advanced`. Playing "counts" for the streak **when a run completes**, not on mere app open (flag 5b) — this makes the streak reflect actual play.

## 3. Outcome Cards (§3) — replaces `PlaceholderOutcomeScreen`

`features/outcome/` (new). Real screen `OutcomeCardScreen(summary: RunSummary)`.

**Flavor content** (`domain/`): three `const` lists of records, each entry authoring **both** a named template and an explicit anonymous fallback so the no-name card (3.4) reads cleanly (never string-hacked):
```
class DeathFlavor { int catalogNo; String named; String anonymous; }
// named: "{name} blinked at the exact wrong moment."
// anonymous: "Blinked at the exact wrong moment."
```
- `death_lines.dart` — **50** entries, `catalogNo` 1–50 (of the aspirational 1000).
- `survived_lines.dart` — **10** entries.
- `eternal_lines.dart` — **6** entries.

`FlavorSelector` (pure): `pick(pool, Random)` → uniform random entry; `render(entry, name)` chooses named vs anonymous by `name.isEmpty`. Adding lines later = append to the list; no schema/code change.

**Card layout** (matches 3.1–3.4): badge (death/survived/eternal colour from `AppColors.red/green/gold`), catalog line ("Death #{catalogNo} of 1000" / "Last-second save" / "Perfect start · {perfectCount}/{eternalCount}"), the flavor line, a stat sub-line built from `RunSummary` ("Peaked at {peak}%", "Down to {min}%"), the `stayalive.app` wordmark, and two actions:
- **Share →** (§4). Primary on death/survived; "Flex it →" label on eternal.
- **Again** → next-run flow (§8 navigation; may pass through an interstitial).

**Percentile copy caveat:** the mockup's "top 0.3%" (eternal 3.3) cannot be truthful without a backend population — there is none. Decision: **drop the percentile**, keep the qualitative flex ("Almost nobody does this"). Flagged.

The whole card body is wrapped in a `RepaintBoundary` (a `GlobalKey`) so §4 can rasterize exactly what's on screen.

## 4. Sharing (§4)

`features/sharing/` (new). Packages: **`share_plus`**, **`path_provider`**.

- **`CardRenderer`** (`application/card_renderer.dart`): captures the outcome card's `RepaintBoundary` via `boundary.toImage(pixelRatio: 3)` → PNG bytes → writes to a single reused temp file in `getTemporaryDirectory()` (e.g. `share_card.png`, overwritten each time so files don't accumulate).
- **`ShareService`** (`application/share_service.dart`): thin wrapper over `Share.shareXFiles([xfile], text: '…stayalive.app')`. The native sheet (4.1) provides IG Stories / WhatsApp / Copy / More — we do **not** hand-build those targets; the OS supplies them.
- **Confirm (4.2):** a lightweight in-app snackbar/toast ("Shared") shown after the sheet returns a success result. Reworded away from "camera roll" per §1 item 2.
- **No 4.3 permission prompt** (§1 item 2).

Web target: `share_plus` supports the Web Share API where available and degrades gracefully; on unsupported browsers, fall back to a download/copy. Flagged as a minor web-parity note, not a blocker (Android is primary).

## 5. Ads (§5) — fake service, real flow

`features/ads/` (new). **No ad SDK dependency.**

- **`AdService`** interface: `Future<void> showInterstitial()`, `Future<RewardedResult> showRewarded()` (`RewardedResult { completed, dismissedEarly, failedToLoad }`).
- **`FakeAdService`** impl: renders our own placeholder creatives (5.1/5.3 are our widgets, styled from the mockup's `.adscreen`), with a countdown timer; the rewarded result is `completed` **only** if the timer fully elapses (honours "credit only on completed view"), `dismissedEarly` on close, and can be told to return `failedToLoad` to exercise 8.3.
- **`AdGate`** (`application/ad_gate.dart`): an in-memory session counter in a **kept-alive** provider (not autoDispose) — show an interstitial after every **3** completed runs (config; mockup says "every 3–4"). Reset only on app relaunch. (Persisting the cadence is unnecessary and would just annoy on relaunch — flagged.)
- **Interstitial placement:** on **Again** from the outcome card, `AdGate` decides; if due, push `InterstitialScreen` (5.1) then continue to the next run's countdown. Never on **Home**, never mid-run (v2 kept the play screen ad-free).
- **Rewarded (5.2–5.4): FOUNDER-RESOLVED — skipped entirely, not built this pass.** It would unlock a card *skin*, and the cosmetics/skins system is out of scope, so a rewarded flow would currently grant nothing real. `AdService.showRewarded()` stays in the interface (for a future pass) but no screens/entry-point call it. Only the interstitial (5.1) ships.
- **Ad failed (8.3):** `AdFailedView` with Retry / Maybe later, shown when `showInterstitial()` returns `failedToLoad`; never strands the player (Maybe later continues the flow).

## 6. Home & Progression (§6) — replaces `PlaceholderHomeScreen`

`features/home/` + `features/progression/` (streak/stats live in `progression`, shared by Home and by `RunController`).

- **`HomeScreen` (6.1):** wordmark + tagline; **daily streak** card (count + 7-segment week bar); three stat tiles (**Best life**, **Eternal**, **Deaths**) read from `RunStatsRepository` via a `statsProvider`; a big **Play** `StickerButton`; a gear icon → Settings; the stat tiles tap through to the full **Stats** screen (6.4).
- **`statsProvider`** (`progression/state/`): a `Notifier<StatsSnapshot>` that reads the repository once into RAM and is `ref.invalidate`d after a run completes and after a reset, so Home reflects fresh totals without polling.
- **Streak advanced (6.2):** shown once when `registerPlay` returns `advanced` — surfaced on return to Home after a qualifying run (a transient flag on `statsProvider`, cleared on display). Not a separate route; an overlay/celebration state on Home.
- **Streak broken (6.3):** shown at Home open when `StreakCalculator.isBrokenAtOpen` is true and the player hasn't played today; gentle framing + "Start a new streak" (→ Play). A Home `WidgetsBindingObserver` re-evaluates on resume so crossing midnight while the app sits open updates correctly.
- **Stats (6.4):** full lifetime list (Best life, Total deaths, Survives, Eternal Humans, Best streak) from the same repository.
- **Collection (6.5): out of scope** (§1 item 7).

**Reconciliation — start-life vs "Best life" (FOUNDER-RESOLVED):** `RunConfig.startLifePercent` changes from `100` to **`50`** — a tuning edit to the already-shipped Play Loop (v2), not a v3 file. This makes "Best life %" and "Peaked at N%" real, non-trivial stats instead of always reading 100.

## 7. Settings (§7)

`features/settings/` (new). Model `AppSettings { bool sound; bool haptics; bool reminder; }`, `SettingsRepository` over the new prefs keys, `settingsProvider` (`Notifier<AppSettings>`, RAM source of truth, write-through).

- **7.1:** Sound toggle, Haptics toggle, **Name** row (shows current name; tap → edit dialog reusing v1 `NameValidator` + `ProfanityFilter`; writes via a new `PlayerProfileNotifier.updateName(String)`), **Daily reminder** toggle (drives §8).
- **Haptics / Sound gating:** `StickerButton` currently fires `HapticFeedback.lightImpact()` unconditionally. Introduce `core/feedback/feedback.dart` — a tiny `Feedback` holder backed by two `ValueNotifier<bool>` (`hapticsEnabled`, `soundEnabled`) that `settingsProvider` updates on change and on load. `StickerButton` (a core widget, deliberately Riverpod-free) consults `Feedback.hapticsEnabled` before buzzing; `AudioService` consults `soundEnabled`. This keeps the core widget decoupled from Riverpod while honouring the toggle.
- **7.2 legal:** Privacy / Terms / Rate → `url_launcher` (§1 item 6 — URLs founder-provided). "Rate the game" opens the store listing (hidden on web). **Reset progress** row (red, guarded).
- **7.3 reset confirm:** double-confirm modal → clears all prefs keys, **cancels any scheduled reminder**, invalidates `playerProfileProvider`/`statsProvider`/`settingsProvider`, then `pushNamedAndRemoveUntil` back to `/` (splash) — which re-runs onboarding (v1 §4 anticipated exactly this). Guard the "Yes, reset" button against double-tap (re-entrancy).

## 8. Notifications / daily reminder (§8.4 + streak) & remaining edge states

`features/notifications/` (new). Packages: **`flutter_local_notifications`**, **`timezone`**.

- **`ReminderService`** interface: `requestPermission()`, `scheduleDaily(hour)`, `cancel()`. Android impl uses `flutter_local_notifications` + `timezone`; **web/iOS use a no-op impl** (same interface-first pattern as ads). Android 13+ `POST_NOTIFICATIONS` requested via the plugin.
- **Opt-in (8.4):** shown **once**, in context, after the streak reaches **day 2** (gated by `reminder_opt_in_shown`), never on cold launch. "Remind me daily" → request permission → on grant, `reminder_enabled = true` + `scheduleDaily(19:00 local)` (default hour — flagged). "No thanks" → leave off; re-enablable only from Settings.
- **Denied permission:** `reminder_enabled` stays false; the Settings toggle, if flipped on later, re-requests and, if the OS has hard-denied, shows a rationale pointing to system settings. Never crashes, never nags.
- **Scheduling idempotency:** exactly one notification id (e.g. `1001`); enabling cancels-then-schedules; on app start, reconcile (if `reminder_enabled` but nothing scheduled, reschedule). `timezone` initialised once in `main()` (Android only).

**Remaining edge states:** 8.1 already done (onboarding v1 name rejection). 8.2 offline deferred (§1 item 8). 8.3 ad-failed handled in §5.

## 11. Memory-safety review (new stateful surfaces)

1. **Notification scheduling across app kills.** Scheduled notifications *should* survive process death (that's their job) — the risk is **duplicate/orphaned** schedules. Handling: a single stable notification id; enable = cancel-then-schedule; on `main()` reconcile (`reminder_enabled` ⇒ ensure exactly one scheduled). Never schedule per-build. `timezone` init exactly once. All plugin calls wrapped so a denied/failed schedule never throws into the UI.

2. **Image render-to-file lifecycle.** `RepaintBoundary.toImage` is async and requires the boundary laid out: trigger capture from a post-frame callback, `mounted`-guard before and after the `await`. **Dispose the `ui.Image`** (`image.dispose()`) after encoding to PNG bytes to avoid leaking native image memory. Reuse one temp filename (overwrite) so cache files don't accumulate. If the boundary's `GlobalKey.currentContext` is null (screen gone), abort the share cleanly.

3. **Ad-service lifecycle (even as a stub).** `FakeAdService`'s countdown uses a `Timer`/`AnimationController` **disposed** on screen dispose; navigation after an ad completes is guarded by a `_handedOff` bool + `mounted` (v1/v2 discipline). Rewarded credit fires **only** on genuine timer completion, never on early dismiss. `AdGate`'s counter lives in a kept-alive provider; it never touches `BuildContext`.

4. **`statsProvider` / `settingsProvider` staleness.** RAM is the source of truth; prefs are write-through. After a run completes and after a reset, the relevant providers are `ref.invalidate`d so Home/Stats/Settings re-read — no stale totals. Writes are fire-and-forget with swallowed errors (repository level), so a failed persist never blocks or crashes the UI.

5. **Streak daily-boundary correctness.** All date math via `StreakCalculator` on **local** epoch-day; `registerPlay` is idempotent for same-day repeat plays. Home re-evaluates streak-broken on `AppLifecycleState.resumed` (observer registered in `initState`, removed in `dispose`) so an app left open across midnight updates. Clock-change/DST edges accepted (flagged as a known coarse approximation).

6. **Reset re-entrancy & teardown.** "Yes, reset" guarded by a `_resetting` bool (single execution); it cancels the reminder, clears prefs, invalidates providers, then `pushNamedAndRemoveUntil('/')` — after which no old screen can reference cleared state (the whole stack is gone).

7. **`BuildContext`/`ref` across async gaps.** Every share, ad, launcher, and permission call is followed by `if (!mounted) return;` before touching `context`/`Navigator`, per the v1 §8 / v2 §9 convention.

8. **Feedback gates.** The `Feedback` `ValueNotifier`s are process-global singletons (no per-widget listeners that could leak); `StickerButton` reads the current value synchronously at tap time rather than subscribing.
