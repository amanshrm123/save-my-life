# Architecture v2

*Living document. Current agreed architecture for the Timing-Tap launch. Per the versioning convention, `vN.md` files are **never edited in place** — this file supersedes `docs/architecture/v1.md` (which stays as the historical record of the feel-first cut). Source of truth for design: `docs/design/screen-library-v3.html` (founder's expanded vision) reconciled against `docs/discovery/TimingTap_OnePager_v1.md` (original locked scope). The next agreed revision lands as `v3.md`.*

---

## 0. What changed from v1, and why

v1 was scoped to a **15–20 day feel-first playable** that answered exactly one question — *does the tap feel skillful enough that a stranger replays and comes back on D1?* — and deferred everything content- or growth-heavy. That was the right cut for de-risking the core loop.

**The founder has now expanded launch scope** to the full screen library in `docs/design/screen-library-v3.html`. v2 brings the following IN that v1 had explicitly OUT:

- **A real first-launch onboarding flow** (screen-library §1): splash, 3 teaching cards, in-context name capture — replacing v1's "minimal-to-none onboarding."
- **A rewarded-ad flow alongside the interstitial** (§5.2–5.4): opt-in rewarded video that unlocks a small set of card skins, with a reward-granted confirmation. v1 shipped interstitial-only.
- **A settings feature module** (§7): sound, haptics, edit-name, daily-reminder toggle, legal/privacy/rate links, and a guarded reset-progress — replacing v1's "settings-lite."
- **Local notifications** for the daily-reminder opt-in (§8.4) — a new retention lever v1 didn't have.
- **Home & progression screens** (§6.1–6.3): a real Home centered on the daily streak, the streak-broken state, and a lifetime-stats screen. v1 only surfaced the streak inline.
- **Edge & error states** (§8): name-rejected, offline reassurance, ad-failed retry, notification opt-in — the "make it feel finished" layer.
- **Play-loop states** (§2): countdown (2.1), pause (2.6), and the polished on-point/miss/final-band treatments (2.2–2.5). The band logic already existed in v1; this is presentation + the two genuinely-new run states (countdown, pause).
- **Outcome polish** (§3.4): the no-name fallback card and name-on-card, plus the share confirm toast and photo-permission prompt (§4.2–4.3).

**Explicitly still deferred to v1.1+:** the **death-collection gallery (screen-library §6.4)** — the doc labels it "Post-v1 candidate" itself, and we respect that. See §6 for the full scope guard, including one further cut I am making deliberately (the cosmetics *economy* behind rewarded ads).

This is a **reconciliation, not a rewrite.** Everything v1 decided correctly and that the new scope does not touch is carried forward unchanged and is *not* re-justified here (see §3).

## 1. Revised timeline — the honest number

**v1 claimed 15–20 days. v2 is 28–32 days end-to-end** (Android live, iOS fast-follow after). That is roughly **+10 working days / two additional weeks** over v1.

I am not keeping the 15–20 label. Bringing in a full onboarding flow, a settings module with its own persistence and legal surface, a second (rewarded) ad type plus the cosmetic it unlocks, local-notification scheduling with runtime permissions, three new Home/progression screens, and four edge/error states is real, buildable work — and it widens the QA and store-compliance surface materially. Pretending it fits the old box would be dishonest and would blow the deadline silently, which is exactly the failure mode the One-Pager's scope guard exists to prevent.

**What genuinely absorbs into existing phases (no calendar cost):**
- The **play-loop state treatments** (2.2–2.5 neutral/on-point/miss/final-band) are presentation on band logic that already exists — they fold into the outcome-wiring phase and the polish pass, not a new phase.
- **Sound/haptics** in settings are just flags; the audio/haptic layer that reads them is the polish pass v1 already budgeted. Settings exposes the toggles; polish builds the thing they toggle.
- **Offline handling is nearly free** — the game is already local-first (§3). The offline state is reassurance UI, not new architecture.

**What is genuinely additive (the ~10 days):** onboarding + name validation (~2d), Home/stats/streak-broken screens (~1.5d), settings module + reset flow (~1.5d), local notifications + opt-in + permissions (~1d), rewarded flow + minimal skins + reward-granted + ad-failed (~1.5d), the countdown/pause run states (~1d), and a wider full-surface QA + store-compliance pass (~+1.5d over v1's).

**The gate discipline is unchanged and non-negotiable:** GATE 1 (does a stranger replay?) still runs first, on real hardware, before *any* of this new scope is built. If Gate 1 fails, none of the expansion happens — we stop and fix the tap. Every day estimate below is *conditional on Gate 1 passing.*

## 3. Tech stack — only the deltas the new scope forces

### 3.1 Carried forward from v1, unchanged and not re-argued
The new scope does not touch these, so they stand exactly as decided in v1:
- **Flutter stable / Dart 3, Android-first** (§1.1).
- **Timing engine**: raw-pointer capture, monotonic `Stopwatch` clock, `CustomPainter` + single `Ticker` for the moving indicator, pure `resolve()` (v1 §1.2). Untouched.
- **Riverpod** (`flutter_riverpod`, plain providers/`Notifier`, no codegen/hooks) as the state layer (v1 §1.3). The new features are new providers; the pattern is identical.
- **Hive** for local persistence behind `ProfileRepository` (v1 §1.4). See 3.4 for how settings/name/skins extend it.
- **`RepaintBoundary` WYSIWYG card capture** (v1 §1.5). A card *skin* is a palette parameter on the same one `CardTemplate` widget — no new capture path.
- **Firebase Analytics only, no backend, Remote Config deferred** (v1 §1.6). Still true. New analytics events are added to the same centralized `AnalyticsEvents` contract (see 3.6).
- **`share_plus` native sheet + best-effort IG Stories deep-link** (v1 §1.8). Unchanged.

### 3.2 Ads — AdMob direct still holds; add a distinct rewarded flow
v1 §1.7's core call is **confirmed: plain AdMob (`google_mobile_ads`), no mediation SDK.** Two placements do not justify AppLovin MAX; mediation is still a post-PMF revenue-optimization problem, and revenue is still not a launch metric. The `AdService` interface seam v1 created is what makes adding a second ad type a contained change.

New decisions the rewarded flow forces:
- **A distinct ad unit and a distinct load/show/result path.** Interstitial is fire-and-forget on a run→run transition; rewarded is a **request → play → result** flow with an explicit outcome. `AdService` gains `loadRewarded()` / `showRewarded()` returning a result the caller awaits.
- **Reward grants ONLY on the AdMob `onUserEarnedReward` callback** — never on ad-close, never on the offer tap (screen-library 5.3 states this explicitly). This is a hard rule the code-reviewer audits, same class of rule as the interstitial-placement rules.
- **Rewarded may fail to fill.** The ad-failed state (§8.3) is *mandatory* for rewarded (interstitials silently no-op on failure; rewarded cannot, because the player initiated it expecting a reward). Failure path = retry / dismiss, player never stranded, reward never granted without a completed view.
- **Placement:** rewarded is opt-in, off the play surface, and never a revive/continue — cosmetics only (see the scope note in §6 on how tightly the *reward* is scoped).

### 3.3 Local notifications — `flutter_local_notifications`, local-only, no FCM
The daily-reminder opt-in (§8.4) needs scheduled local notifications. **Decision: `flutter_local_notifications`, purely local — no Firebase Cloud Messaging, no push server.** This keeps the game backend-free and local-first (an FCM server is exactly the kind of infra the One-Pager rules out). A single daily reminder is scheduled/cancelled client-side.
- **Android 13+ requires the `POST_NOTIFICATIONS` runtime permission**; iOS requires an authorization request. Both are asked **in context** — after streak day 2–3 (screen-library 8.4) — **not** on first launch. A denied permission degrades silently (toggle reflects OS state; no nagging).
- **Store impact:** notifications are added to the privacy policy and the Play Data Safety form.

### 3.4 Settings & name — extend the existing `ProfileRepository`, don't add a second store
Per the design, settings and name-editing **write back through the existing Hive `ProfileRepository`** (v1 §1.4). Decision: **do not introduce a separate `SettingsRepository`.** The persisted settings (sound on/off, haptics on/off, reminder on/off, display name) are a handful of fields living alongside the existing counters in the same Hive box, exposed via added methods on the one repository interface. Adding a second repository would be a speculative abstraction the flat-layout discipline (v1 §2) rejects.
- **Name validation is a pure, testable function** (`name_validator.dart`): length cap (12 chars per the mockup's "4/12") + a bundled local profanity list. No network. It powers both the onboarding name-capture (1.5) and the name-rejected edge state (8.1), and it must run **before** a name can reach a shared card.
- **No-name fallback** (3.4): when name is empty/skipped, `CardTemplate` uses name-agnostic phrasing — a data path through the same widget, not a second template.

### 3.5 Offline — reaffirm local-first; add a lightweight connectivity signal
Offline is **mostly a non-issue by design** — the game plays 100% offline (v1 §1.4). The only network touchpoints are AdMob and Analytics, both of which tolerate offline (Analytics buffers locally; ads simply don't fill). The offline reassurance state (§8.2) is **UI, not architecture.**
- **Decision:** add `connectivity_plus` (small, well-maintained) purely to drive the passive offline banner and to suppress pointless ad requests while offline. This is the one new dependency I'll accept for edge-state honesty.
- **Copy correction — flag for game-ux-designer:** screen-library 8.2 says "stats sync when you're back." **There is no stats sync** (no cloud, no accounts — v1 §1.6 stands). The offline copy must be reassurance only and must not promise a sync that doesn't exist. Analytics events buffer locally via the Firebase SDK; that's the only thing that "sends when back."

### 3.6 Analytics — same contract, new events
Still Analytics-only. Added to the centralized `AnalyticsEvents` file: `onboarding_complete`, `name_set{hasName}`, `reminder_opt_in{granted}`, `rewarded_offered`, `rewarded_completed`, `skin_unlocked{skinId}`, `ad_failed{type}`. D1 retention remains the single success metric; these are watch-only secondaries. No new cloud infra.

## 4. Revised module / package layout

Same discipline as v1 §2 — **flat, feature-first, no speculative abstractions.** New features are new folders under `features/`; the two existing interface seams (`CardContentSource`, `AdService`) are reused, not multiplied. Additions are marked `+NEW`.

```
lib/
  main.dart                      # Hive init, Firebase init, notifications init, runApp
  app/
    app.dart                     # root widget, theme, ProviderScope
    router.dart                  # +NEW screens: Splash/Onboarding, Home, Play, Outcome, Settings, Stats
  core/
    clock.dart                   # MonotonicClock — unchanged
    timing_config.dart           # bands, life deltas, adaptive k (off) — unchanged
    theme.dart, constants.dart
    connectivity.dart            # +NEW connectivity_plus wrapper (offline signal)
  features/
    timing_engine/               # unchanged (Days 1–2, done)
      timing_engine.dart | tap_surface.dart | indicator_painter.dart
    run/
      run_controller.dart        # +extended: countdown phase, pause/resume, run freeze
      outcome_resolver.dart      # unchanged pure resolver
      run_state.dart             # +phases: countdown, paused
    cards/
      card_content_source.dart | bundled_card_source.dart | card_picker.dart
      card_template.dart         # +extended: name / no-name fallback, skin (palette) param
    share/
      card_capture.dart          # unchanged (RepaintBoundary -> PNG)
      share_service.dart         # +confirm toast, +photo-permission prompt (4.2/4.3)
    ads/
      ad_service.dart            # +extended interface: interstitial (v1) + rewarded flow
      rewarded_controller.dart   # +NEW request->play->result, reward-on-callback-only
    cosmetics/                   # +NEW — deliberately minimal (see scope guard §6)
      card_skin.dart             # data: 2–3 palette variants for CardTemplate
      skin_controller.dart       # unlocked-set state; persists via ProfileRepository
    onboarding/                  # +NEW
      onboarding_controller.dart # first-launch flag, step index, name capture
      onboarding_flow.dart       # splash + 3 teach cards + name capture (1.1–1.5)
      name_validator.dart        # pure: length cap + profanity list (powers 1.5 & 8.1)
    settings/                    # +NEW
      settings_controller.dart   # reads/writes ProfileRepository; sound/haptics/reminder/name
      settings_screen.dart       # 7.1/7.2 (incl. legal/rate links)
      reset_flow.dart            # 7.3 guarded reset-progress
    notifications/               # +NEW
      notification_service.dart  # flutter_local_notifications wrapper; schedule/cancel/permission
      reminder_optin.dart        # in-context opt-in (8.4), after streak day 2–3
    home/                        # +NEW
      home_screen.dart           # 6.1 streak-first home + Play
      stats_screen.dart          # 6.3 lifetime totals
      # streak-broken (6.2) is a state of home, not a separate module
    analytics/
      analytics_service.dart | analytics_events.dart   # +new events (3.6)
    persistence/
      profile_repository.dart          # +methods: settings, name, unlocked skins
      hive_profile_repository.dart     # +fields in existing box
    daily_streak/
      daily_streak_controller.dart     # unchanged; now surfaced by home/ + drives reminder
assets/
  cards.json                     # 30–50 cards (hard cap, unchanged)
  profanity.txt                  # +NEW bundled list for name_validator
  art/
```

**Dependency rule unchanged:** features depend downward on `core` and on repository/service *interfaces* only. The timing engine and run/outcome logic stay pure and headlessly testable. `cosmetics/`, `notifications/`, `onboarding/`, `settings/` are all leaf features that depend on `ProfileRepository` and services — nothing depends on them.

**No collection-gallery module exists** — deferred (§6). No `SettingsRepository`, no cosmetics economy/inventory module, no FCM — all deliberately absent (§6).

## 5. Revised phase plan (agent ownership per phase)

Agents: **flutter-developer** (client), **backend-engineer** (Firebase/cloud), **game-ux-designer** (UX/flows), **tester** (QA), **code-reviewer**, **player-reviewer** (fun/feel), **play-store-specialist** / **app-store-specialist**.

Days are cumulative and conditional on Gate 1 passing. Total: **28–32 days.**

### Days 1–2 — DONE. Walking skeleton + timing engine.
Carried from v1. Code-reviewed. See §2.

### Days 3–5 — Feel prototype + **GATE 1 (kill/continue)** — *not yet run; do this next*
- **Build:** life bar wired to bands; adaptive `k` scaffolded but off (fixed bands ship); on-device tuning of the real ±ms values into `timing_config.dart`; minimal juice (tap flash + one sound). **+Add the countdown (2.1)** here — the 3-2-1 sets the shared rhythm and is part of what a stranger judges as "feel." Minimal on-point/miss flash (2.3/2.4) for legibility only.
- **Owns:** flutter-developer + **player-reviewer** (decisive voice). game-ux-designer tunes feedback timing. tester runs ≥2 real Android devices/refresh rates.
- **GATE 1:** *Does a stranger replay unprompted?* < kill → stop, fix the tap, build nothing below. feels skillful → lock the ms values and continue. Slippage here comes out of buffer, not by cutting later phases.

### Days 6–11 — Three outcomes + cards + share + streak + share edge states
- **Build:** `outcome_resolver.dart` (Death / Survived / Eternal, locked rules incl. life clamp); `bundled_card_source.dart` + `card_picker.dart` + `card_template.dart`; **+no-name fallback (3.4)** and name-on-card wiring; `card_capture.dart` + `share_service.dart` **+confirm toast (4.2) +photo-permission prompt (4.3)**; `daily_streak/`; `hive_profile_repository.dart` (loss/lifetime counters, seen-card set). Play-loop state treatments (2.2–2.5) applied here.
- **Owns:** flutter-developer (outcomes, share, persistence, streak). game-ux-designer (outcome/card/play-state visual design, share-CTA). **Content authoring in parallel** (contracted): 30–50 death lines + Survived/Eternal pools + few art variants. tester verifies outcome truth table + valid PNG on device + share permission path.
- **Done when:** full loop plays end-to-end on device; all three outcomes reachable and correct; no-name and named cards both render; share sheet opens with confirm toast; streak increments across days.

### Days 12–14 — Onboarding + Home/progression
- **Build:** `onboarding/` splash + 3 teach cards + name capture (1.1–1.5); `name_validator.dart` (length + profanity) **+name-rejected edge state (8.1)**; first-launch-only gating. `home/` Home (6.1, streak-first) + Stats (6.3) **+streak-broken state (6.2)**.
- **Owns:** flutter-developer (onboarding controller, home/stats, validation). game-ux-designer (teaching-card flow, home layout, streak surfacing). tester (name_validator unit tests, once-only onboarding, skip path).
- **Done when:** first launch runs onboarding once, captures/validates or skips a name that flows onto cards; Home shows the streak and launches Play; streak-broken renders; stats reflect local totals.

### Days 15–17 — Settings + notifications + offline
- **Build:** `settings/` (sound, haptics, edit-name, reminder toggle, legal/privacy/rate links, guarded reset 7.3) writing through `ProfileRepository`; `notifications/` (`flutter_local_notifications`, schedule/cancel daily reminder, `POST_NOTIFICATIONS`/iOS auth, in-context opt-in 8.4 after streak day 2–3); `core/connectivity.dart` + offline reassurance state (8.2, reassurance-only copy — no sync claim).
- **Owns:** flutter-developer (settings, notifications, connectivity). game-ux-designer (settings rows, opt-in framing, offline copy — corrects the "sync" wording per 3.5). backend-engineer (confirms notifications are local-only, flags the Data-Safety/privacy additions). tester (reset flow, reminder fires next day, permission-denied degrade).
- **Done when:** settings persist and take effect; reminder schedules only after opt-in and only with OS permission; reset double-confirms and clears Hive; offline banner appears without blocking play.

### Days 18–20 — Ads (interstitial + rewarded) + analytics
- **Build:** `ad_service.dart` interstitial (v1 rules: run→run only, after card, freq-capped, preloaded) + rewarded flow (`rewarded_controller.dart`: request→play→result, **reward on `onUserEarnedReward` only**) + reward-granted state (5.4) + **ad-failed retry (8.3)**; `cosmetics/` minimal (2–3 palette skins, unlocked-set persisted, applied via `CardTemplate` skin param); analytics wired to the full event set (3.6).
- **Owns:** flutter-developer (both ad types, cosmetics, analytics wiring). **backend-engineer** (Firebase Analytics config, verify D1 + secondaries land; confirm `CardContentSource` seam still Remote-Config-ready but build no RC). **code-reviewer** (audits: interstitial never over play/death surface; rewarded grants only on callback; ad-failed never strands).
- **Done when:** interstitial respects cap + placement with next run preloaded; rewarded grants a skin only on completed view; ad-failed retries cleanly; skins render on cards; events verified in Firebase.

### Days 21–23 — Cross-feature polish + pause
- **Build:** the polish/juice pass (audio + haptic layer that settings toggles read; final-band styling 2.5; on-point/miss polish); **+pause overlay (2.6)** with run freeze/resume/restart/quit; a full feel pass across the now-larger surface.
- **Owns:** game-ux-designer (directs polish against feel, not decoration). flutter-developer (pause/run-freeze state, audio/haptic layer). code-reviewer (pause must not perturb the timing path — clock pauses cleanly, no drift on resume).
- **Done when:** sound/haptics respond to settings; pause freezes and resumes a run without timing drift; polish merged without regressing tap latency.

### Days 24–27 — Full real-device QA + build + store listing/assets
- **Build:** release build config, icon, listing copy, screenshots, feature graphic, privacy policy (**ads + analytics + notifications** disclosure), Play **Data Safety** form, content rating, AdMob UMP consent.
- **Owns:** **tester** (full pass: once-only onboarding, name validation, streak across day boundary, reminder scheduling + permission states, rewarded fill/no-fill, interstitial cap, offline, reset, cold-start clock init). **play-store-specialist** (listing + Data Safety + policy — ads/analytics/notifications disclosures, families/ads policy). game-ux-designer (store creative). flutter-developer (release build, consent flow).
- **Done when:** signed release build passes QA offline and online across the full surface; listing + Data Safety + rating pass compliance review; no P0/P1 open.

### Days 28–32 — Store submission + review buffer + **GATE 2 (live)**
- **Build:** submit to Play (internal → closed/production). Fix review kickbacks.
- **Owns:** play-store-specialist (submission + response). flutter-developer (hotfix on kickback). tester (verify exact submitted build).
- **GATE 2:** live on Play Store → start watching D1 (Floor <10% kill, 15–25% OK, >30% strong).
- **iOS follow:** flip build target, submit via app-store-specialist — fast-follow, not in the box.

## 6. Scope guard — what is IN vs still OUT

The governing test is unchanged from the One-Pager: *if a feature does not (a) help answer "does the tap feel good / do they come back D1" or (b) move D1 retention (or is a store/legal requirement), it is out.* The founder's expansion widens what qualifies under (b) and adds the "feel-finished" edge states — but it does **not** repeal the test.

### Now IN (was OUT in v1)
Onboarding flow (1.1–1.5) · name capture + validation · Home + Stats + streak-broken (6.1–6.3) · Settings + reset (7) · local notifications / daily reminder (8.4) · rewarded-ad flow + reward-granted (5.2–5.4) · minimal card skins · countdown (2.1) · pause (2.6) · no-name fallback (3.4) · share confirm + photo permission (4.2–4.3) · edge/error states: name-rejected, offline, ad-failed (8.1–8.3).

### Still OUT — deferred to v1.1+
- **Death-collection gallery (screen-library §6.4)** — deferred per its own "Post-v1 candidate" label. No module, no stub, no partial wiring. It's the natural v1.1 headline feature once D1 is proven.
- **A cosmetics *economy*.** This is a deliberate cut I am making, not one handed to me. The screen library shows rewarded ads unlocking a card skin, and I've included the rewarded *flow* and a **minimal 2–3 palette skins** (cheap, because a skin is one data param on the existing single `CardTemplate` widget). What I am **refusing to build for launch** is the vertical *behind* that mockup: a skin shop, an inventory system, currency, multiple reward types, or a skin-selection gallery. That vertical is a week-plus of work, moves *zero* D1 retention (revenue is still not a launch metric per the One-Pager), and would silently re-open the "monetization optimization" scope the One-Pager explicitly closed. If Days 18–20 come under timeline pressure, **the rewarded/skins slice is the first thing to cut** — the interstitial (the one placement v1 committed to) stays; the skins go, and the game is unharmed.
- **Full 1000-card library** — still a hard 30–50 cap; the rest grow post-launch via the template engine + Remote Config.
- **Banner ads, IAP.**
- **Global leaderboards, Remote Config, accounts, custom backend, cloud sync.** Firebase stays Analytics-only. (Note the offline copy in 8.2 must not promise a sync that doesn't exist — §3.5.)
- **Push notifications via FCM.** Local notifications only — no push server.
- **Adaptive difficulty tightening.** Fixed bands ship; `k` scaffolded off.
- **Rich per-death animations.** Templated text + few static art variants + palette skins only.
- **iOS in the box.** Android-first, iOS fast-follow.

Writing down what we are **not** building remains the primary deadline protector. Any request to add one of these before Gate 2 is out of scope by default and must be re-argued against the governing test.
