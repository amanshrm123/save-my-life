# Stay Alive — Architecture v2

**Scope:** Play Loop & in-run states only (mockup Section 2, screens 2.1–2.8).
**Builds on:** Architecture v1 (onboarding, merged). v1 stays as-is — this is a new doc, not an edit.
**Project:** `timing_tap` · Android + web dev targets · Flutter, `flutter_riverpod ^3.3.2`, `shared_preferences ^2.5.5` already present.

Two engineering practices are **givens, not open questions** (carried forward as general good practice, not as any reference to the fully-discarded prior mechanic):
- **G1 — Monotonic clock only.** All in-run timing uses a `Stopwatch`-backed clock. Never `DateTime.now()`.
- **G2 — Raw `Listener` for the stop tap.** The precision STOP input is captured via `Listener.onPointerDown`, never `GestureDetector`/`InkWell`, to avoid gesture-arena latency on the one input that decides the score.

---

## 0. The mechanic (as read fresh from Section 2)

A **run** is a series of **stop attempts** against a life bar:

```
Home ──Play──▶ Countdown (3-2-1, named)
                    │
                    ▼
   ┌──────────── ARMED ──────────────┐   center "STOP AT <target>" plate shown (gold);
   │  tap center plate ─▶ RUNNING     │   bottom STOP button dimmed
   │  stopwatch counts UP from 0      │
   │  center plate hidden; small      │   RUNNING: numplate shows live count-up;
   │  "Target <t>" reminder remains   │   bottom STOP now live
   │  tap STOP ─▶ evaluate            │
   └──────────────┬───────────────────┘
                  ▼  compare stop-time vs target → tier → life delta → flash
        ┌─────────┴──────────┐
     continue            terminal
   (re-arm next        (death / survive / eternal)
    target)                   │
                              ▼  hand off to PlaceholderOutcomeScreen
```

The player is racing the stopwatch **up to** the target and must freeze it as close to the target instant as possible (can undershoot or overshoot). Nail it → gain life; miss → lose life; hit 0% → gone. At very low life the run enters a sudden-death "final band."

Pause (2.8) freezes the run at any time.

## 1. State management — extend the existing Riverpod setup (do not replace)

v1 established: `preferencesServiceProvider` (overridden in `main()`), `playerProfileRepositoryProvider`, `playerProfileProvider` (`AsyncNotifierProvider`). v2 adds **one** new provider and reuses the profile:

```
runControllerProvider  =  NotifierProvider.autoDispose<RunController, RunState>
        │  reads:
        └── playerProfileProvider   (for the countdown greeting name only)
```

- **`RunController extends Notifier<RunState>`** (synchronous Notifier, not Async — the run state is pure in-RAM game state, nothing to load). It owns the mutable `GameClock` as a private field and exposes intent methods: `startCountdown()`, `arm()`, `startRunning()`, `registerStop()`, `pause()`, `resume()`, `restartRun()`, `enterFinalBand()`.
- **`.autoDispose`** so every entry into Play starts from a clean slate and no stale run survives Home→Play→Home→Play. `ref.onDispose` stops/resets the `GameClock`. (Decision — flagged.)
- **The live 60fps clock display does NOT go through Riverpod.** Rebuilding the provider graph every frame would be wasteful and jittery. Instead the screen owns a `Ticker` that reads `clock.elapsed` each frame and pushes to a `ValueNotifier<Duration>`; only the numplate widget listens (`ValueListenableBuilder`). Riverpod carries **phase transitions and life**, which change a few times per second at most.

**Why this split mirrors v1's philosophy:** the authoritative game state lives in RAM (the Notifier + the `GameClock`); the per-frame display is a scoped, controller-free view concern. Nothing about a run is persisted (see §6).

## 2. Timing engine — precision & data types

**`GameClock`** (`domain/game_clock.dart`, pure Dart, unit-testable):
- Wraps a single `Stopwatch` (G1). API: `start()`, `stop() → Duration`, `reset()`, `Duration get elapsed`, `bool get isRunning`.
- Internal precision is whatever `Stopwatch.elapsed` gives (microseconds). **All scoring math is done in `Duration` (microsecond-backed), reduced to integer milliseconds for tier comparison.** No floating-point seconds anywhere in the decision path.

**The load-bearing capture path (G2):**
```
Listener(onPointerDown: (_) => ref.read(runControllerProvider.notifier).registerStop())
```
`registerStop()`'s **first line** is `final stopped = _clock.elapsed;` — a direct synchronous read, one call hop from the pointer-down, no async gap, no gesture arena. Everything after (tier calc, life delta, setState) is post-capture and cannot pollute the measured instant.

**Display format — `SS:CC` (seconds : hundredths), founder-resolved (§Flag 2, re-resolved).** After playtesting concern that `MM:SS` with a 0–5 minute target made the game boring (dead air with zero skill value — confirmed independently by the player-reviewer pass, which also found the wait invited a "tap STOP immediately, eat a cheap Miss, reroll a shorter target" exploit), the founder switched back to the original `SS:CC` proposal: `formatClock(Duration) → "SS:CC"` (e.g. `03:47` = 3.47 s), target randomized within **`[2.00 s, 6.00 s]`** (see §7 — this is the change that actually fixes the pacing problem, not the display format alone). The live count-up visibly ticks hundredths (a real "blur" of digits, standard stopwatch feel) and freezes on stop. This keeps the wait itself short and legible while still giving the scoring tiers (§3) real precision to bite into.

## 3. Scoring & tiers — decision: **3 tiers** (Perfect / Hit / Miss)

The legend pills ("Hit +2% / Miss −5%") and the outcome flashes ("PERFECT +3%", "MISS −5%") together imply three tiers; the legend simply omits Perfect and the concrete example screens omit Hit. (Founder-resolved: 3 tiers is canonical — see §Flag 1.)

**`scoring.dart` (pure, unit-testable):** `StopTier classify(Duration error)` where `error = (stopElapsed - target).abs()`:

| Tier | Boundary (|error|) | Life delta | Flash |
|------|--------------------|-----------|-------|
| **Perfect** | ≤ 60 ms | **+3%** | green "PERFECT +3%" |
| **Hit** | 60 ms < e ≤ 180 ms | **+2%** | green "HIT +2%" |
| **Miss** | > 180 ms | **−5%** | red "MISS −5%" (+ shows the gap) |

The ms boundaries are independent of the display format and stand unchanged under the `SS:CC` decision. They are defaults living in `RunConfig` (§7) for playtest tuning. Rationale for the bands: these are *anticipatory* taps (the player watches the hundredths climb toward the target), so a tight ±60 ms Perfect is skill-gated but achievable, and >180 ms is a clear miss. Life clamps to `[0, 100]`, starts at **100%**.

**Display vs tier nuance (intentional skill mechanic):** the hundredths digits blur visibly during a fast count-up, so even though the precision is technically visible, landing within the ±60 ms Perfect window is still a real reflex/timing skill, not something read off the frozen display after the fact. A stop that freezes on `03:47` when the target is also `03:47` is likely a Perfect or Hit; the exact tier is confirmed by the flash. Decision: **show the true captured value**, do not snap the display to the target on Perfect (flagged — snap-to-target is a juicier alternative).

## 4. Run outcomes & the final band

**`RunOutcome { death, survived, eternal }`** — the "three ways it ends" onboarding taught (card 3).

**Final band (screen 2.7) — decisions:**
- **Threshold:** after a life delta is applied, if `0 < life ≤ 5%` the run enters the final band for the **next** attempt (mockup shows 4%; I set the trigger at ≤5%). If `life ≤ 0` at any point → immediate `death`.
- **Semantics — sudden death, terminal either way:** in the final band there is no more incremental ±life. One attempt decides the run:
  - non-miss (Perfect **or** Hit) → run ends as **`survived`** (the "last save" / clutch-win — feeds the Section 3.2 Survived card pool, out of scope to build).
  - miss → run ends as **`death`**.
- This matches the copy ("one clean stop saves you", "next miss is fatal") and onboarding's "survive a last save" (a distinct positive ending, not a heal-and-continue). Flagged — alternatives: require Perfect (not just Hit) to survive; or make a final-band success restore life and continue the run.

**Eternal (added — flagged):** onboarding card 3 and Section 3.3 define Eternal as "three perfect taps from cold." To make the loop reach all three promised endings end-to-end, the state machine detects: **first 3 attempts of a run all Perfect → run ends as `eternal`.** The coordinator's state-machine sketch omitted this; included so the loop is complete, but flagged as possibly out of scope.

## 5. State machine & state shape

**`RunPhase`** (enum): `countdown`, `armed`, `running`, `stopped`, `finalBandArmed`, `finalBandRunning`, `paused`, `ended`.

**`RunState`** (immutable, `copyWith`; `domain/run_state.dart`):
```
RunPhase   phase
int        lifePercent          // 0..100
Duration   target               // current attempt's target
int        runNumber            // lifetime counter, persisted (§6, revised)
int        deaths               // lifetime counter, persisted (§6, revised)
int        attemptIndex         // 0-based; for Eternal (first 3)
bool       perfectStreakIntact  // true until first non-Perfect; for Eternal
StopTier?  lastTier             // drives the flash
Duration?  lastStopElapsed      // frozen value to render after a stop
RunOutcome? outcome             // set only in phase == ended
RunPhase?  phaseBeforePause     // to restore on resume
```
The `GameClock` is **not** in `RunState` (it's a mutable resource, held by `RunController`).

**Transitions (all in `RunController`):**
```
countdown ──(timer done)──▶ armed
armed ──(tap center plate, guard: phase==armed)──▶ running        [clock.reset(); clock.start()]
running ──(tap STOP, guard: phase==running)──▶ stopped            [stopped = clock.stop()]
stopped ──(evaluate)──▶
     life<=0                         ▶ ended(death)
     eternal condition met           ▶ ended(eternal)
     0<life<=5                       ▶ finalBandArmed
     else                            ▶ armed (new target)         [brief flash dwell first]
finalBandArmed ──(tap center)──▶ finalBandRunning ──(STOP)──▶
     non-miss ▶ ended(survived)
     miss     ▶ ended(death)
any(armed|running|finalBand*) ──(pause)──▶ paused
paused ──(resume)──▶ armed | finalBandArmed   (in-flight RUNNING attempt is discarded — see §8)
paused ──(restart)──▶ countdown/armed with life=100, fresh target, counters reset-for-run
paused ──(quit)──▶ pop to PlaceholderHomeScreen
ended ──(navigate once)──▶ PlaceholderOutcomeScreen(outcome)
```
The brief post-stop flash dwell (`lastTier` visible ~500–700 ms) before re-arming is a UI timer in the screen, `mounted`-guarded, not a domain concern.

## 6. Counters, persistence — decision (FOUNDER-RESOLVED, revised): **lifetime totals, persisted**

Founder overrode the original session-only proposal: Run/Deaths must be genuine cross-session lifetime totals — every completed run increments the total played, and a `death` outcome additionally increments the total deaths, surviving app relaunches (not just the current session).

- New `shared_preferences` keys: `kKeyTotalRunsPlayed` (int, default 0), `kKeyTotalDeaths` (int, default 0) — added to `core/persistence/preferences_keys.dart`/`preferences_service.dart` alongside the existing onboarding keys. No `kPrefsSchemaVersion` bump needed — these are new independent keys, not a reshape of an existing one.
- `RunStatsRepository` (`features/play_loop/data/run_stats_repository.dart`) wraps the two new prefs fields, mirroring `PlayerProfileRepository`'s pattern: `totalRunsPlayed`/`totalDeaths` getters, `recordRunCompleted({required bool wasDeath})` for the terminal write.
- `RunController._freshRunState()` seeds `RunState.runNumber = repo.totalRunsPlayed + 1` and `RunState.deaths = repo.totalDeaths` on every fresh run (i.e. every non-restart entry) — this run in progress is the *next* one; deaths reflects the lifetime total so far since this run hasn't ended yet.
- `advanceAfterDwell()`'s three terminal branches (`endDeath`/`endEternal`/`endSurvived`) all call `RunStatsRepository.recordRunCompleted` — any outcome counts as a completed run; only `death` also increments the deaths total. The write is fire-and-forget (`unawaited`) since nothing in the UI gates on it, and `RunStatsRepository` swallows its own write failures (architecture v1 §8.7 precedent) rather than throwing into the Notifier.
- **"Restart run" does not call `recordRunCompleted`** — abandoning a run's progress via Restart is not a completion, so it must not inflate the lifetime totals. `restartRun()` carries `runNumber`/`deaths` over unchanged from current state rather than re-reading from the repository.
- **Life, target, and other run-in-progress fields remain pure RAM state**, reset on every fresh run/restart — only the two lifetime counters are persisted.

The existing `player_profile` prefs (name) are still only **read** for the countdown greeting; nothing about the profile itself is written from this feature.

## 8. Navigation & the playable handoff

**Entry point (fixes the current dead-end):** `PlaceholderHomeScreen` (`lib/features/placeholder/placeholder_home_screen.dart`) currently only shows text. Add a **"Play" `StickerButton`** (coral) that does `Navigator.pushNamed(context, AppRoutes.play)`. Add `static const String play = '/play';` to `AppRoutes`, and register `AppRoutes.play → PlayLoopScreen` in `app.dart`'s `routes` map (same style as the existing three routes).

**Per-run open — decision: countdown only, NO repeated splash/5s loader.** See §Flag 4. Entering Play goes straight to the 3-2-1 countdown (2.2); the cold-launch splash (v1) is not shown again per run.

**Outcome handoff — `PlaceholderOutcomeScreen(outcome)`** (genuinely working, not a stub, mirroring `PlaceholderHomeScreen`):
- Shows which of death / survived / eternal occurred (badge + one line, using `AppColors.red/green/gold`).
- **"Again"** → `Navigator.pushReplacement` a fresh `PlayLoopScreen` (autoDispose gives a clean run).
- **"Home"** → `Navigator.popUntil` back to `PlaceholderHomeScreen`.
- Reached via `Navigator.pushReplacement` from the play screen when `phase == ended` (so STOP/back can't return into a finished run).

This keeps the loop end-to-end playable (Home → Play → run → outcome → Again/Home) with real outcome cards (Section 3) explicitly deferred.

## 9. Memory-safety review (mandatory before implementation)

The new risk surface vs onboarding is a **live monotonic clock, a Ticker, and one latency-critical raw input**. Each risk + required handling:

1. **App backgrounded mid-run → `Stopwatch` jumps forward on resume → corrupt stop-time.** This is the headline correctness issue. `PlayLoopScreen` implements `WidgetsBindingObserver`; on `didChangeAppLifecycleState(inactive|paused)` while `phase ∈ {running, finalBandRunning}`, **auto-pause**: `clock.stop()`, discard the in-flight attempt, transition to `paused`. On resume the player returns to `armed`/`finalBandArmed` for the same target with no life penalty. This guarantees a stop-time is only ever taken from a foreground, continuously-running clock. Register the observer in `initState`, remove it in `dispose`.

2. **`Ticker` / `AnimationController` disposal.** The screen's display `Ticker`, the countdown timer/controller, and the flash controller are all created in `initState`/as `late final` and **disposed** in `dispose()`. `GameClock` is stopped+reset via `ref.onDispose` in the `RunController`. No controller is created in `build`.

3. **Double-tap on STOP (the critical input).** `registerStop()` is a no-op unless `phase ∈ {running, finalBandRunning}`, and its first action after capturing `elapsed` is to move `phase → stopped`. A second `onPointerDown` in the same frame therefore finds the guard already closed. A `_stopConsumed` latch (reset only on re-arm) is the belt-and-braces backstop against multi-pointer / rapid re-fire.

4. **Double-tap on the center ARM plate.** `startRunning()` is a no-op unless `phase ∈ {armed, finalBandArmed}`; a second tap after the plate hides (phase already running) does nothing.

5. **Re-entrant navigation on run end.** When `phase == ended`, the screen navigates exactly once, guarded by a `bool _handedOff` flag; any `context`/`ref` use after an `await` (e.g. flash dwell) is preceded by `if (!mounted) return;` — the same discipline v1 §8 established.

6. **Per-frame rebuild cost.** The live count-up is confined to `stopwatch_plate.dart` via `ValueListenableBuilder<Duration>` fed by the Ticker → `ValueNotifier`. The rest of the screen (life bar, chips, buttons) rebuilds only on Riverpod phase/life changes, not per frame. No `setState` on the whole screen at 60fps.

7. **Ticker firing after dispose / while app not visible.** The display Ticker's callback guards on `mounted`; when the app is inactive the auto-pause (risk 1) has already stopped consuming clock reads. Flutter's `TickerMode` mutes the ticker off-screen; do not fight it with a manually-resurrected timer.

8. **Pause "clock scrubbing" exploit.** Manual pause during RUNNING is treated exactly like backgrounding: the in-flight attempt is discarded and the player resumes at `armed` for the same target. This removes any "pause just before the target second, resume, tap" cheese. (Flagged — alternative: allow resume to continue the exact in-flight count.)

9. **Stale run across Home↔Play cycles.** `runControllerProvider` is `.autoDispose`; leaving Play tears down the controller and `GameClock`, so re-entering always starts a clean run. Prevents a resurrected half-finished run.

10. **`GameClock` single-ownership.** Exactly one `GameClock`, owned by `RunController`; never instantiated in a widget. `elapsed` is exposed read-only for the display Ticker.

## 10. Flags for founder sign-off

Founder-resolved items are marked as such; the rest remain open for a decision.

1. **3 tiers (Perfect +3% / Hit +2% / Miss −5%) — FOUNDER-RESOLVED.** Confirmed 3 tiers, not 2; the 2.3/2.4 legend is treated as incomplete (it omits Perfect). Boundaries per §3.

2. **Display format `SS:CC` (seconds.hundredths) — FOUNDER-RESOLVED (re-resolved).** Originally proposed, then overridden to `MM:SS`/0–5min, then switched back after that combination proved boring in practice (no skill value in the wait, plus a reroll exploit — see §2's note). `SS:CC` with the short `[2.00s, 6.00s]` range (§3 below) is the final, settled decision.

3. **Target range `2.00 s`–`6.00 s` — FOUNDER-RESOLVED (re-resolved).** Chosen per attempt within that range, `SS:CC` granularity. (Distribution shape — uniform vs weighted, and whether it drifts as life changes — remains a tuning detail in `RunConfig`, but the bounds are settled.)

4. **No per-run splash + 5s loader — countdown only — FOUNDER-RESOLVED.** Per-run open is the 3-2-1 countdown (2.2) only; the splash stays a cold-launch-only beat. The mockup 2.1 per-run splash+5s-loader is dropped.

5. **Final band = sudden death, terminal either way — FOUNDER-RESOLVED.** Non-miss → `survived` (ends the run as the clutch win); miss → `death`. Still open as a tuning/detail question: (a) whether survival should require a *Perfect* rather than any non-miss, and (b) the exact threshold (I use ≤5%; mockup depicts 4%).

6. **FOUNDER-RESOLVED (revised):** Run/Deaths are genuine lifetime totals, persisted via `shared_preferences` (`RunStatsRepository`), surviving app relaunches — not session-only as originally proposed. See §6.

7. **Pause "Restart run" = full reset** (life → 100%, fresh target, current run's progress abandoned; does not increment the Run counter). **"Quit to home"** → the existing `PlaceholderHomeScreen`. Confirm both, especially whether Restart should count as a new Run.

8. **Eternal ending included (first 3 taps all Perfect → `eternal`).** Onboarding promises three endings, so I added Eternal detection to make the loop reachable end-to-end. The state-machine sketch omitted it — confirm it's in scope for this pass (vs deferring Eternal entirely to when its outcome card is built).

9. **Perfect does NOT snap the display to the target** (shows the true captured whole-second value). Alternative: snap/lock the displayed seconds to the target on Perfect for extra "it locked on!" juice. Which do you prefer?

10. **`runControllerProvider` is `.autoDispose`** (clean run per entry). Trivial but flagged since it affects whether any run state could ever linger across navigation.

*Out of scope (explicitly deferred, same pattern as v1):* Outcome Cards (Section 3), Sharing (4), Ads (5), Home/Progression (6), Settings (7), Edge/error states (8). The Play Loop hands into a genuinely-working `PlaceholderOutcomeScreen` for death/survive/eternal and back to `PlaceholderHomeScreen` for quit — real cards replace the placeholder when Section 3 is built.
