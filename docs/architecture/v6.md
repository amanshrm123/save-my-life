# Stay Alive — Architecture v6

**Scope:** the Play Loop's **scoring model** and **clock display format** only (mockup section `#b`, screens 2.1–2.8), plus the repairs elsewhere in the app that this change forces.
**Revises:** architecture v2 §2 / §3 / §4 / §7 and v2 §Flag 1 / §Flag 2 / §Flag 3; partially revises v3 §Flag 10. v1–v5 stay as-is — this is a new doc, not an edit.
**Founder ask, verbatim:** "binary hit/miss change (visible MM:SS target, 'TAP'/'stop on the number' button, 'Hit: safe'/'Miss: -10%' legend pills, HIT/MISS flying pill, death at 0% life)".
**Confirmed reversal:** the founder was shown the full decision history and confirmed they want this, knowing it reverses two previously-resolved decisions (v2 Flag 1 "3 tiers is canonical" and v2 Flag 2/3 "`SS:CC` + a short target range is the final, settled decision"). This doc does not re-litigate either reversal. It does resolve what the ask leaves open, and it does surface the consequences the ask does not mention.

Two engineering practices remain **givens, not open questions**, carried forward from v2 unchanged and untouched by anything below:
- **G1 — Monotonic clock only.** All in-run timing uses the `Stopwatch`-backed `GameClock`. Never `DateTime.now()`.
- **G2 — Raw `Listener` for the stop tap.** `PrimaryActionButton` captures the scoring input via `Listener.onPointerDown`, and `RunController.handlePrimaryPointerDown`'s **literal first statement** is `final captured = _clock.elapsed;`. This is a copy/scoring change; it must not move, wrap, or delay that statement.

## 1. What the ask reverses, stated plainly

For the record, so no future pass has to reconstruct it:

| | v2/v3 resolution | v6 |
|---|---|---|
| Tier count | 3 (Perfect / Hit / Miss) — v2 §Flag 1, "3 tiers is canonical" | **2 (Hit / Miss)** |
| Life on a good stop | Perfect +3%, Hit +2% | **Hit 0% ("safe")** |
| Life on a bad stop | Miss −5% | **Miss −10%** |
| Can life increase mid-run? | Yes | **No, ever** |
| Display | `SS:CC` ("4:70") — v2 §Flag 2, "final, settled" | **`M:SS.CC` ("0:04.70")** |
| Eternal trigger | First 3 attempts all Perfect | **First 12 attempts all non-Miss** |

The original mockup (`docs/mockups/timingtap_screen_library_v3-4.html` §`#b`) only ever showed two legend pills and MM:SS-shaped targets; `docs/design/play-loop-v1.md` §3.2/§8 already records that the third tier and `SS:CC` were architecture *inferences beyond the literal mock*. So D1 and D10 are a partial return to mock ground truth, not a novel invention. The parts of the ask that are genuinely new — the button verb, the "safe" framing, the doubled miss cost — are resolved in §4 and §6 rather than assumed.

**The two things the ask does not mention but breaks.** Both are resolved below; neither is optional:
1. With Hit neutral, life is **monotonically non-increasing**. `RunOutcome.survived` (final band) becomes numerically unreachable (§4.3), and `peakLifePercent` becomes a constant (§7.2).
2. With no Perfect tier, `RunOutcome.eternal` has no tier to key off (§5) — and, less obviously, **the run loses its only upper terminator**: a player who never misses would otherwise play forever.

## 2. Display format — resolved to `M:SS.CC`

### 2.1 What "visible MM:SS target" most plausibly means

The founder previously ran the MM:SS experiment and killed it. `run_config.dart` records why in its own doc comment: the target range was "re-resolved after the MM:SS/0-5min range proved boring in practice", and v2 §2 adds that the player-reviewer independently found the dead air had zero skill value plus a "tap STOP immediately, eat a cheap Miss, reroll a shorter target" exploit.

The founder is therefore very unlikely to be asking for minute-long waits again. What changed since then is the *readout*, not the wait: `SS:CC` renders 4.70 s as **`4:70`**, which is not a valid clock reading in any format — no clock has 70 seconds. Read as a legibility complaint ("the number on the plate should look like a time"), the ask is entirely reasonable and entirely compatible with short targets.

**Resolution: keep real time and short targets; make the readout unambiguously clock-shaped by giving it a real minutes field and a decimal separator before the hundredths.**

### 2.2 Format spec (implementable directly)

`formatClock(Duration)` returns `M:SS.CC`:

```
totalCentis = duration.inMilliseconds ~/ 10        // truncate, never round
minutes     = totalCentis ~/ 6000
seconds     = (totalCentis ~/ 100) % 60
centis      = totalCentis % 100
return '$minutes:${seconds.pad2}.${centis.pad2}'
```

| Input | Output |
|---|---|
| `Duration.zero` | `0:00.00` |
| `200 ms` | `0:00.20` |
| `2000 ms` | `0:02.00` |
| `4700 ms` | `0:04.70` |
| `4900 ms` | `0:04.90` |
| `59_990 ms` | `0:59.99` |
| `65_430 ms` | `1:05.43` |
| `3_600_000 ms` | `60:00.00` |

- **Minutes is NOT zero-padded**; seconds and hundredths always are. This carries the existing convention forward (today's `clock_format.dart` deliberately does not pad the leading field) and moves it to the new leading field. Padding seconds is mandatory — `0:4.70` would be wrong.
- Minutes will always read `0` under the current target range. That is the honest cost of honoring MM:SS with sub-5-second targets, and it is the one part of D10 worth a founder sentence (§13 flag 1). The format rolls into minutes correctly if a long target is ever configured, so nothing has to be rewritten if the founder later changes their mind.
- The format applies to **both** the target and the live count-up, since `formatClock` is shared by `primary_action_button.dart`, `stopwatch_plate.dart`, and `_RunningContent`/`_StoppedContent`'s "Target …" line. The player must be comparing like with like.

### 2.3 Rejected alternatives

- **`0:SS` with a 10x-scaled "life clock"** (3.5 real seconds displayed as `0:35` of game time). Literally MM:SS-shaped, 4 glyphs, keeps the fast digit blur. Rejected: it invents a time unit that every future spec, test, and story-copy author has to remember to convert, and it makes the displayed target semantically fake. Not worth it to save two glyphs.
- **`M:SS` at true 1-second precision with 15–45 s targets.** Rejected: 17-plus attempts per run at 30 s each is an 8-minute run, and a target the player can only aim at to the nearest second turns a ±180 ms band into invisible luck. This is exactly the failure mode that was already rejected once.
- **`SS.CC` ("04.70")** — unambiguous and short, but has no MM field, so it does not answer the ask.
- **Keeping `SS:CC`.** Does not answer the ask.

### 2.4 Precision is a display concern only

Internal timing stays microsecond-backed `Duration` math reduced to integer milliseconds for the single band comparison (v2 §2, unchanged). Display precision (centiseconds) and classification precision (milliseconds) remain deliberately decoupled — the `hitBandMs = 180` window is 18 display units wide, which is what makes the band *achievable* rather than a display-equality lottery. `_randomTarget()`'s centisecond quantization stays correct because the smallest displayed unit is still a centisecond.

`_statusLabel`'s Miss readout ("Stopped · off by 0.42") is a **delta, not a clock**, and stays a plain seconds decimal. Unchanged.

## 3. Scoring — two tiers, one band

`scoring.dart`:

```
StopTier classifyStop({target, stopped, config}):
    errorMs = (stopped - target).abs().inMilliseconds
    return errorMs <= config.hitBandMs ? StopTier.hit : StopTier.miss

int lifeDeltaForTier(StopTier tier, RunConfig config):
    hit  -> config.hitDelta    // 0
    miss -> config.missDelta   // -10
```

**`lifeDeltaForTier` survives** (answering the ask's biggest open question explicitly). It could collapse to a single ternary at the call site, but keeping it means the life economy stays in one pure, unit-testable function, and re-introducing any Hit gain later is a one-line config change rather than a re-plumb. `hitDelta = 0` stays a real config field for the same reason: it makes "Hit is safe" a *tuned value*, not a hardcoded assumption spread across the scoring path and the flash/legend widgets.

**Band value: keep `hitBandMs = 180`, do not widen it yet.** Under three tiers, 180 ms was the outer forgiveness edge and 60 ms was where the reward lived. Under two tiers the outer edge is the whole difficulty knob, and using the *outer* value (not the inner 60 ms) is deliberate: since a good stop no longer buys anything, skill now only buys *not losing*, so the pass band has to be generous or every run is a fast death. Holding 180 also keeps the first playtest interpretable — the miss penalty already doubled, and moving two knobs at once makes attribution impossible.

`hitBandMs` is the **primary post-playtest difficulty dial**, and the expected direction of travel is *wider*, not narrower, if runs feel too short.

**`_scheduleAutoMiss` needs no change.** It already keys off `state.target.inMilliseconds + config.hitBandMs + config.autoMissGraceMs`, i.e. the outer band plus grace. Deleting `perfectBandMs` does not touch it.

## 4. The life economy

### 4.1 "Hit: safe" means exactly what it says

Hit grants nothing. Life can never increase during a run. This is the load-bearing consequence of the ask and everything in §4 and §7 follows from it. Stated as invariants the tests should assert:

- `lifePercent` is monotonically non-increasing within a run.
- `peakLifePercent == startLifePercent` for every run, always.
- `minLifePercent == lifePercent` at all times (the low-water mark is the current value).
- Therefore `minLifePercent == 0` for every `death`, and `== finalBandThresholdPercent` for every `survived`.

### 4.2 `startLifePercent` stays 50 — it is now an attrition budget

The number's meaning changed even though the number doesn't. v3 §Flag 10 lowered it 100 -> 50 specifically so "Best life %" and "Peaked at N%" would be non-trivial stats — growth headroom. Under D3 there is no growth, so that rationale is void (§7.2 handles the fallout). What `startLifePercent` now controls is one thing only:

```
misses_to_death = startLifePercent / -missDelta
```

= **5 misses** at 50/−10. That is the right run length and it is why 50 is kept:

- At a plausible 75–90% hit rate, 5 misses is roughly 17–30 attempts, roughly 85–150 s per run including the 600 ms dwell and arm reaction. That fits a loop whose output is a shareable card and an interstitial cadence.
- The obvious alternative, `startLifePercent = 100`, doubles that to 10 misses and roughly 3–5 minutes per run. Too long.
- Getting a full bar *and* 5 misses would need `missDelta = -20`, which overrides an explicit founder number. Not doing that.
- 50 is already shipped and already founder-resolved; not stacking a third reversal onto this pass.

Accepted cost: the bar starts half-empty with no way to refill, so the top half of the life bar is permanently dead. Thematically this reads as "you start already fragile", which is on-brand for a game called Stay Alive, and §7.1's threshold rebase keeps the avatar expressive across the range that is actually used. This is the one number most likely to want revisiting after a playtest (§13 flag 3).

### 4.3 `finalBandThresholdPercent` 5 -> 10, or the `survived` ending dies

With `startLifePercent = 50` and `missDelta = -10`, life only ever takes the values **50, 40, 30, 20, 10, 0**. The existing trigger is `0 < newLife <= 5`, which **no reachable life value satisfies**. Left at 5, the final band never arms, `finalBandArmed`/`finalBandRunning` become dead phases, `_PendingAdvance.endSurvived` becomes dead code, and `RunOutcome.survived` — one of the three endings onboarding card 3 promises and one of three tiles on the Home screen — becomes unreachable. This is not a tuning nit; it silently deletes a third of the game's output.

**Fix: `finalBandThresholdPercent = 10`, with the invariant `finalBandThresholdPercent == -missDelta`.**

Two independent reasons this is the right value rather than an arbitrary one:
1. It is the only value that makes the final band mean "exactly one miss from zero", which makes `play_hud_bar.dart`'s already-shipped copy `"<n>% · next miss is fatal"` literally true rather than approximately true.
2. It makes the config self-consistent under any future retuning of `missDelta`. Worth an assert or a `run_config_test.dart` case so a future `missDelta` edit can't quietly orphan the final band again.

Resulting run shape: 4 normal misses (50 -> 40 -> 30 -> 20 -> 10), then the final band arms, then one sudden-death attempt. Still 5 misses total, exactly as §4.2 budgeted.

### 4.4 The final band now applies the delta, so death is genuinely at 0%

Today the final band applies **no** life delta at all (v2 §4: "sudden death, terminal either way"). Combined with D6 that would mean a final-band death ends the run with the bar still showing 10%, and the founder explicitly asked for "death at 0% life".

**Fix:** in `_resolveStop`'s `finalBandRunning` branch, apply `lifeDeltaForTier` exactly as the normal branch does. From 10%, a miss lands on **exactly 0** and the run ends `death`; a hit applies 0 and the run ends `survived` with life still at 10%. The only thing that remains special about the final band is that a non-miss *terminates the run as a win* instead of re-arming — which is the actual semantic content of "sudden death". The life math no longer needs a special case.

Benefits beyond satisfying the ask: `minLifePercent == 0` for every death on both paths (previously 0 on the normal path, 10 on the final-band path — an inconsistency nobody had noticed), and the life bar visibly empties on the fatal stop instead of freezing at 10%.

`lastStopWasFinalBand` and the "SURVIVED"/"MISS"-without-percentage flash (design v1 §2.7) stay exactly as shipped. The final-band flash still shows no percentage even though a delta is now applied — that frame's job is to announce the ending, not the arithmetic.

### 4.5 Full life-value table

| Attempt outcome | Life before | Life after | Phase after |
|---|---|---|---|
| Hit (normal) | any | unchanged | `armed`, new target |
| Miss (normal) | 50 | 40 | `armed` |
| Miss (normal) | 20 | 10 | `finalBandArmed` |
| Hit (final band) | 10 | 10 | `ended` / `survived` |
| Miss (final band) | 10 | **0** | `ended` / `death` |
| 12th consecutive Hit from cold | 50 | 50 | `ended` / `eternal` |

## 5. Eternal — kept, redefined around the hit streak

`RunOutcome.eternal` is currently detected only via `perfectStreakIntact && attemptIndex >= eternalPerfectCount`. Delete the Perfect tier and that mechanic has nothing to key off. The ask does not mention Eternal at all, so this is resolved here.

### 5.1 Do not retire it. Three independent reasons, one of them decisive.

1. **It is now the run's only upper terminator.** Under D3 a player who never misses never loses life, and there is no timeout, no attempt cap, and no other win condition. Without Eternal, a skilled player's run **never ends**. Retiring Eternal doesn't just remove an ending; it leaves the loop without a terminating branch for its best players. This alone settles it.
2. **It is promised to the player already.** `onboarding_screen.dart` card 3 reads "Die, survive a last save, or go Eternal. All shareable." Retiring Eternal makes shipped onboarding copy a lie.
3. **A lot of shipped surface would be stranded:** the `Home` screen's third stat tile (`snap.totalEternal`) and `stats_screen.dart`'s "Eternal Humans" row would sit at 0 forever; `kKeyTotalEternal`, `kKeySeenStoryIdsEternal`, `kKeyLastStoryIdEternal`, `RunStatsRepository.totalEternal`, `StatsSnapshot.totalEternal`, the entire `OutcomeTierPalette.eternal` gradient theme, `AppColors.eternal*` (five tokens), and the authored `eternal` story pool in `tools/story-content/stories.json` would all become dead.

### 5.2 New definition

**Eternal = the first `eternalHitCount` attempts of a run, none of them a Miss.** A direct structural swap of "Perfect" for "non-Miss":

```
hitStreakIntact = state.hitStreakIntact && tier == StopTier.hit
eternalReached  = hitStreakIntact && newAttemptIndex >= config.eternalHitCount
```

Renames: `RunConfig.eternalPerfectCount` -> `eternalHitCount`; `RunState.perfectStreakIntact` -> `hitStreakIntact`. Both renames are mandatory, not cosmetic — leaving "perfect" in a codebase with no Perfect tier is exactly the sort of stale name a reviewer should reject.

**Keep `hitStreakIntact` as an explicit field. Do not derive it from life.** Under this economy `hitStreakIntact` is provably equivalent to `lifePercent == startLifePercent`, and deriving it would delete a field. Rejected: that equivalence is an *accident of the current life economy*, and it would break silently the day any life gain or heal is reintroduced, misfiring Eternal instead of failing loudly. Explicit intent over clever derivation. The equivalence is still worth asserting in a test, as a canary.

### 5.3 `eternalHitCount = 12`

Two forces pull opposite ways: as a terminator it wants to be small (a flawless run must actually end), as a prestige badge it wants to be large. 12 attempts is roughly 60–75 s of flawless play, which lands a flawless run at a comparable length to the death path's 85–150 s — both terminators produce similarly-sized sessions, which is the property that matters most.

Be straight with the founder about the consequence (§13 flag 4): **Eternal becomes materially easier than it is today.** Twelve stops inside ±180 ms is a different kind of demand than three inside ±60 ms, and the true frequency depends entirely on the population hit rate, which nobody here knows yet. Rather than pretend to a number, ship 12 and treat it as the second-most-important playtest dial after `hitBandMs`, with an explicit calibration rule:

```
eternalHitCount ≈ log(target_eternal_rate) / log(observed_hit_rate)
```

Bounded by: it must stay low enough that a flawless run terminates inside roughly 20 attempts. If the founder wants Eternal genuinely rare, 15–18 is the range to try first, and the `outcome_card_shell.dart` chip copy "✨ Eternal · Top 0.3%" — already flagged in v4 §1 as unverified bragging that no code computes — gets more obviously fictional the lower this number goes.

### 5.4 `RunSummary.perfectCount` -> `attemptCount` (recommended)

`RunSummary.perfectCount` is fed `state.attemptIndex`, i.e. total attempts, not a Perfect count — a pre-existing naming inaccuracy that becomes actively misleading once no Perfect tier exists. It has **exactly one producer and zero consumers** today (nothing in `lib/features/outcome/` reads it), so renaming it to `attemptCount` is near-zero-risk. Its doc comment's example, "Perfect start · {perfectCount}/{eternalCount}", should read "{attemptCount}/{eternalHitCount}".

## 6. Copy

### 6.1 The button verb — "TAP" resolved

The ask's `'TAP'` matches neither the mock ("STOP AT `<target>`" / "STOP") nor current code, so it needs a decision. It is almost certainly a verb change rather than a request to drop the target off the button — dropping the target would remove the single most important piece of information on the arm screen. Supporting evidence: onboarding card 1's shipped headline is already **"Tap on the number"**, so the founder is very likely aligning the Play Loop's verb with the teaching copy the player has already been given.

**Resolution: one verb, `TAP`, in all four `PrimaryActionLook`s.**

| Look | Phase | Today | v6 |
|---|---|---|---|
| `armStart` | `armed`, `finalBandArmed` | micro "STOP AT" + target 56dp | micro **"TAP AT"** + target (size per §6.3) |
| `stopNormal` | `running` | "STOP" 34dp + "stop as close to `<target>` as you can" | **"TAP"** 34dp + **"tap on the number"** |
| `stopFinal` | `finalBandRunning` | "STOP" 34dp + "one clean stop saves you" | **"TAP"** 34dp + "one clean stop saves you" (unchanged) |
| `dwellDimmed` | `stopped` | same content as `armStart`, inert | same content as `armStart`, inert |

Semantics labels follow: `'Tap at ${formatClock(target)}'` (armStart), `'Tap'` (stopNormal/stopFinal), `'Next target ${formatClock(target)}'` (dwellDimmed, unchanged).

`stopFinal`'s sub-label is deliberately left alone. The ask didn't mention the final band, the copy is still accurate, and it is the only thing differentiating sudden death from a normal attempt in that look.

### 6.2 "stop on the number" -> "tap on the number"

**Recommendation: use "tap on the number", not the ask's literal "stop on the number".** With the button label now reading TAP, "stop on the number" mixes verbs in a two-line composition, and "tap on the number" is *verbatim* onboarding card 1's headline — the player has already been taught this exact phrase. This is a one-word founder confirm (§13 flag 2), not a blocker; if the founder wants "stop", it's a one-line change.

**Replacing the sub-label loses nothing.** `_RunningContent` already renders `'Target ${formatClock(target)}'` above the live plate, in both the normal and final-band frames, so the target stays on screen during RUNNING independently of the button. The old sub-label was redundant with it, which is part of why the shorter copy is an improvement rather than a trade.

### 6.3 Legend pills — exactly two

`legend_pills.dart` drops from three pills to two:

- `Hit: safe` — **literal string, no interpolation.** There is no number to show, and hardcoding the word is the honest rendering of `hitDelta == 0`.
- `Miss: ${config.missDelta}%` -> renders `Miss: -10%`. Keep the interpolation so the pill can never drift from `RunConfig`.

The `Wrap`-instead-of-`Row` layout stays (two pills will not wrap on any phone, but there is no reason to remove the safety). The final-band branch — a single "Nail it → Survive" pill replacing the row entirely — is unchanged.

The file's doc comment currently says the 3-pill layout was "extrapolated beyond the mock's literal 2-pill layout". That comment must be rewritten, not just left in place: the mock's 2-pill layout is now canonical.

### 6.4 Flying pill

`outcome_flash.dart` drops its `StopTier.perfect` arm and changes the Hit label:

| Case | Today | v6 |
|---|---|---|
| Perfect, normal | `PERFECT +3%` | *(gone)* |
| Hit, normal | `HIT +2%` | **`HIT`** |
| Miss, normal | `MISS -5%` | **`MISS -10%`** (interpolated) |
| Non-miss, final band | `SURVIVED` | `SURVIVED` (unchanged) |
| Miss, final band | `MISS` | `MISS` (unchanged) |

`HIT` is bare — no percentage, no "+0%" — for the same reason the legend pill says "safe": there is no delta to report. Green/red `good` colouring, the `ValueKey(state.attemptIndex)` entrance tween, the `Semantics(liveRegion: true)` announcement, and the final-band no-percentage rule are all unchanged. Per the ask this is the lowest-risk part of the change.

`play_loop_screen.dart`'s `_onStopped` switch collapses its `perfect`/`hit` arms into one; the haptic and `audio.playHit()` behaviour for a good stop is unchanged.

### 6.5 Onboarding card 2 — a required repair, not a nicety

`onboarding_screen.dart` card 2 currently reads:

> **Mind your life** — "Nail it, gain life. Miss, lose it. Hit 0% and you're gone."

"Nail it, gain life" becomes **factually false**. A player taught that will read a flat life bar after a good stop as a bug.

**New copy: "Nail it, stay safe. Miss, lose 10%. Hit 0% and you're gone."** It keeps the three-beat rhythm, keeps the card's own "Hit 0%" line (which D8 confirms is still exactly right), and mirrors the legend pills' "safe" wording so the teaching and the HUD agree. Card 1 ("Tap on the number") and card 3 ("Die, survive a last save, or go Eternal") both stay valid as written — card 3 only because §5 keeps Eternal alive.

This drags onboarding into a Play Loop pass, which is unavoidable: onboarding's entire job is teaching this rule, and the rule changed.

## 7. Consequences elsewhere in the app

These are downstream of D3 and are not part of the founder's ask. They are not optional to *address*; §7.1 is in scope for this pass, §7.2 is scoped as Phase 2.

### 7.1 Avatar fill colour bands go stale — rebase them (in scope)

`lib/features/avatar/domain/avatar_fill_band.dart`: `>=60 -> green`, `>=20 -> coral`, else `redDark`.

Reachable in-run life values are now 50, 40, 30, 20, 10, 0. **`green` becomes unreachable in the Play Loop.** And because §7.2 freezes `bestLifePercent` at 50, green becomes unreachable on the Home avatar too — a designed three-band expression collapses to two, app-wide, silently.

**Fix (D17): rebase to `>=40 -> green`, `>=20 -> coral`, else `redDark`.** That gives 50/40 green, 30/20 coral, 10/0 redDark — two attempts per band, an even drain across the whole run, and the in-run `LifeAvatar` becomes a genuinely expressive gauge (it now only ever drains, never refills, which makes the animation *more* readable than before, not less).

Two-line change to a pure function, plus its unit test, plus `docs/design/home-avatars-v1.md` §3.2/§3.5 which records the old thresholds as "architect-confirmed". Note the shared blast radius: this function also colours the Home avatar card and the avatar-picker preview tiles, so the designer must eyeball all three surfaces, not just the Play Loop.

### 7.2 `peakLifePercent` / `bestLifePercent` / Home avatar fill freeze (Phase 2)

Because life never rises, `peakLifePercent == startLifePercent == 50` for every run, forever. `StatsController.registerRunCompletion` computes `bestLifePercent = max(bestLifePercent, summary.peakLifePercent)`, so after the very first completed run:

- `stats_screen.dart`'s "📈 Best life" row reads **`50%` permanently**.
- `home_screen.dart`'s `HomeAvatarCard(bestLifePercent: snap.bestLifePercent)` — the largest element on the Home screen, and its only continuous progression signal — is **frozen at a half-full avatar forever**.

This is exactly the outcome v3 §Flag 10 lowered `startLifePercent` to 50 to *prevent*. The mechanism it relied on no longer exists.

**Recommendation (D19): repoint both surfaces at `bestRunAttempts`** — the highest `attemptIndex` reached in any single run — and normalize the avatar fill as `min(100, bestRunAttempts * 100 / eternalHitCount)`. That is a strictly better progression signal than "best life" ever was under either economy: it moves every time a player beats their own longest run, and it reaches a **full, green avatar exactly when the player goes Eternal**. "How close your best run got to Eternal" is a legible, motivating meter; "best life" under a no-heal economy is a constant.

Cost, and why it is Phase 2 rather than this pass: one new prefs key, a `StatsSnapshot` field, a `StatsController` write, `RunSummary.attemptCount` (already present, see §5.4), copy changes on two screens, and a Home mockup revision. That is a progression change, not a scoring change, and bundling it would blur what the playtest is actually measuring.

**Interim state if Phase 2 slips: Home shows a permanently half-full avatar and a constant "Best life 50%".** Visible, not broken. The founder should be told, and it is their call whether to bundle (§13 flag 5).

### 7.3 Story-copy placeholders degenerate

`story_renderer.dart` substitutes `{min}` and `{peak}`. Under the new economy:

- `{peak}` is always `startLifePercent`. It is currently used by no authored beat; it should now be documented as **do not use** rather than merely "currently unused".
- `{min}` is `0` for every death and `finalBandThresholdPercent` for every survive. `tools/story-content/stories.json` uses it twice, both in the **survived** pool: `"Saved at {min}%."` (line 34) and `"Calm, at {min}%."` (line 70). Both will render **"Saved at 10%." / "Calm, at 10%."** on every single survived card, forever — variety copy that has become a constant.

Not a code defect (the renderer is correct), but a content defect the remote-config/content owner must fix by rewriting those two headlines without `{min}`. Flagged, not fixed here — `stories.json` is remote-config content, out of this pass's code scope.

## 10. Memory / lifecycle review (CLAUDE.md rule 7)

This app is deliberately RAM-resident, so this section is mandatory even when — as here — the answer is mostly "nothing new is retained".

**Structurally inert.** No new provider, no new `Timer`, no new `Ticker`/`AnimationController`, no new listener or observer, no new stream or subscription, no new file/image/cache resource, no new persisted key. `RunState`'s field count is unchanged (one `bool` renamed, none added), so per-run state size is byte-identical. `StopTier` loses a const enum value. `RunController` keeps its single `GameClock`, single `Random`, and single `_autoMissTimer`, all with their existing `ref.onDispose` teardown.

Enumerated risks:

1. **`formatClock` allocation at 60fps — the only genuinely new cost.** It is called once per frame from `StopwatchPlate`'s `ValueListenableBuilder` during `running`/`finalBandRunning`. It already allocates a `String` per frame; the new format allocates roughly two more short-lived `String`s per call (a second `padLeft` plus the wider interpolation). At 60fps that is a few hundred bytes per second of nursery garbage — negligible, and generational GC handles it without a young-gen pause that would be visible at this scale. **Required discipline:** keep the implementation a single interpolation over integer arithmetic. Do **not** reach for `intl`'s `DateFormat` (allocates a formatter, far heavier, and would drag a dependency into a hot path), do **not** build intermediate `List`s or use `RegExp`, and do **not** add a memoization cache keyed on `Duration` — such a cache would be unbounded across a run and would trade a few hundred harmless bytes per second for a genuine leak. This is the one line in the whole change where an "optimization" would make memory worse.
2. **Text layout cost per frame.** 7 glyphs instead of 4 at 52dp means slightly more paragraph layout per frame, still one small `Paragraph` per frame, still inside the existing `RepaintBoundary` around the plate (which is retained deliberately, per the shipped comment isolating the 60fps digits from `LifeAvatar`'s heavier `CustomPainter`). No new boundary should be added; each one costs a retained layer.
3. **Unbounded run length is now possible in principle.** Under D3 a player who never misses loses no life, so `eternalHitCount` is the only thing that ends their run (§5.1). If it were ever mis-set to 0 or a negative, or if the eternal check were accidentally short-circuited, a run could continue indefinitely. Confirmed safe: **nothing accumulates per attempt.** `RunState` holds no per-attempt history list or log; each stop overwrites `lastTier`/`lastStopElapsed`; `attemptIndex` is a single `int`. An unbounded run is memory-flat. `OutcomeFlash`'s `key: ValueKey(state.attemptIndex)` creates a fresh widget per attempt and disposes the previous one — framework-managed, no accumulation. A `run_config_test.dart` case asserting `eternalHitCount >= 1` is cheap insurance.
4. **Auto-pause invariant preserved.** The change touches classification and copy only, never the clock, the lifecycle observer, or the discard-in-flight-attempt rule. A backgrounded `Stopwatch` still can never yield a stop-time.
5. **G2 latency path preserved.** `PrimaryActionButton._onPointerDown` still calls `widget.onTap()` as its literal first statement before the cosmetic press animation, and `handlePrimaryPointerDown` still reads `_clock.elapsed` first. Label/sub-label changes are pure `_buildContent()` edits below that line. A reviewer should treat any movement of those two statements as a blocking defect regardless of how the copy changed.
6. **`autoDispose` teardown unchanged.** Leaving Play still tears down the controller, clock, and auto-miss timer, so no stale run survives a Home <-> Play cycle.
7. **Longer average runs (if `startLifePercent` is ever raised).** More attempts per run means more `AnimatedSwitcher`/`TweenAnimationBuilder` cycles, all framework-disposed, and no growth in retained state per §10.3. No mitigation needed; noted so it isn't re-derived if the founder retunes.

**Net: this change reduces branch count and retains nothing new. The only new allocation is transient, per-frame, and explicitly bounded by the §10.1 discipline.**
