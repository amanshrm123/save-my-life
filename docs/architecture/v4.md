# Stay Alive — Architecture v4

**Scope:** redesign of the existing **Outcome Cards** feature to the new 9:16 "story card" format per `docs/mockups/timingtap_card_stories.html`.
**Revises:** architecture v3 §3 (Outcome Cards). v1/v2/v3 stay as-is — this is a new doc, not an edit.
**Unchanged by this pass:** the Play Loop, Home/Progression, Settings, Ads, Notifications, and the sharing *mechanism* (v3 §4) — only what the card draws, and where its content comes from, changes.

---

## 0. What actually changes

| | Current (v3 §3, shipped) | New (v4) |
|---|---|---|
| Layout | Badge pill **above** a separate bordered card box | **One unified card**: chip + icon top row · headline + story middle · tagline + wordmark + store badges footer |
| Aspect | Fills available height (device-dependent) | **9:16 story format** (fixed `AspectRatio`) |
| Content fields | `catalogLine` + flavor line + `subLine` | **3 randomized slots**: `headline`, `story`, `icon` |
| Catalog no. | "Death #247 of 1000" | **Gone** (not in the new mockup) |
| Stat sub-line | "Peaked at 61%." derived from `RunSummary` | **Gone as its own line** — stats fold into story/headline via numeric placeholders (§1) |
| Content source | Synchronous local pools, picked in a `Provider` | **`OutcomeStoryService`** interface, local impl now, remote later — async |
| Loading | None (synchronous) | **Min-2s branded loader**, every time |
| Failure | N/A | All 3 slots render literal **"N/A"** |
| Death palette | Light/paper | **Dark/inverted** (fixed, not a toggle) |
| Eternal chip | "✨ Eternal Human" (percentile dropped in v3) | **"✨ Eternal · Top 0.3%"** — restored as unverified flavor |
| Store badges | None | **Decorative** App Store + Play badges in footer |

Files deleted: `domain/flavor.dart`, `presentation/widgets/outcome_badge.dart`. Files renamed/reshaped: `*_lines.dart` → `*_beats.dart`, `flavor_selector.dart` → `story_selector.dart` + `story_renderer.dart`.

## 1. Content model

### Decision: **headline + story are bundled into one pooled `StoryBeat`; the icon is a separate, independently-drawn pool.**

The founder's brief fixes the icon as independent ("independently randomized from the headline/story, not paired 1:1 with them"). It does *not* require headline and story to be independent of each other — and the mockup proves they must not be:

- Death card 1: headline **"One tap too late."** + story "…had it. 15:98… 15:99… and froze."  → a **late** death.
- Death card 2: headline **"Blinked. Died."** + story "…panicked at 3% life and slammed the tap a whole half-second **early**."

Cross-pairing those two independently drawn slots produces "One tap too late." above a story about tapping early — a literal self-contradiction, and it would happen roughly half the time. The headline is a compressed restatement of the story's punchline, so the two are semantically welded. The icon is safely independent because it's tonally generic: ⏰️ and 😵 both read fine over any death story.

This still satisfies "3 configurable slots" — all three vary run to run — while only declining the one pairing the founder didn't ask for. Flagged (§7 flag 1).

```
// domain/story_beat.dart
class StoryBeat {
  final String headline;    // NOT name-templated; may contain {min}/{peak}
  final String named;       // story, contains literal {name}; may contain {min}/{peak}
  final String anonymous;   // story, name-free rewrite
}
```
`death_beats.dart` (50 entries), `survived_beats.dart` (10), `eternal_beats.dart` (6) — same seeded counts as today (v3 §1 item 4), each existing line gaining a headline. `EternalFlavor.sub` and `DeathFlavor.catalogNo` are **dropped** (no sub-line, no catalog line in the new layout).

### Icon pools

```
// domain/story_icons.dart
const deathIcons    = ['⏰️', '😵', '💀', '🪦', '⚰️', '💥'];
const survivedIcons = ['😮‍💨', '🆘', '🫀', '🙏', '😅'];
const eternalIcons  = ['✨', '👑', '🏆', '🌟'];
```
Plain `String`s (not codepoints) — see §5.

### Numeric placeholders — required by the mockup

The new layout deletes the derived stat sub-line, but the mockup's own copy still surfaces run stats *inside* the story and headline: **"Saved at 3%."** (headline) and "panicked at **3% life**" (story). That number is `RunSummary.minLifePercent`. So the stats aren't lost — they're absorbed into authored copy via placeholders.

**Decision:** the renderer substitutes `{name}` (story only), plus `{min}` and `{peak}` (headline **or** story) from `RunSummary.minLifePercent` / `peakLifePercent`. This is a two-line extension of today's `render()`, which already does `replaceAll('{name}', name)`.

**Do not** author literal clock values into copy. The mockup's "15:98… 15:99…" implies ~16-second targets, but v2's founder-resolved target range is **2.00–6.00 s** under `SS:CC`, so that line is stale placeholder data. No `{target}`/`{stop}` placeholders this pass — `RunSummary` doesn't carry them and extending it isn't worth it. Flagged (§7 flag 2).

### Resolved content object

```
// domain/outcome_story_content.dart
class OutcomeStoryContent {
  final String headline;   // already substituted
  final String storyNamed; // still contains {name} so the widget can color the span
  final String storyAnonymous;
  final String icon;
  final bool isFallback;   // true == the N/A path
  static const naFor = /* headline:'N/A', storyNamed:'N/A', storyAnonymous:'N/A', icon:'N/A' */;
}
```
`{name}` deliberately survives into the widget layer (exactly as today) so the name span keeps its own tier color; `{min}`/`{peak}` are substituted in the service since they need no styling.

**Static, non-configurable per tier** (never "N/A", never fetched): chip label + palette, tagline "One tap saves you — or ends you.", the 💓 Stay Alive wordmark, and the store badges.

| tier | chip |
|---|---|
| death | `💀 You died` |
| survived | `🆘 Survived` |
| eternal | `✨ Eternal · Top 0.3%` |

Eternal's "Top 0.3%" is restored **as unverified bragging copy only** — founder-resolved, explicitly reversing v3 §3's drop. It is not a measured percentile and no code computes it.

## 2. The fetch-simulation service

```
// application/outcome_story_service.dart
abstract class OutcomeStoryService {
  Future<OutcomeStoryContent> fetchStory(RunSummary summary);
}
```

- **`LocalOutcomeStoryService`** (this pass) — draws from the local pools, substitutes `{min}`/`{peak}`, returns near-instantly. Carries `bool forceFailure = false`, mirroring `FakeAdService`'s exact pattern; when true it returns `OutcomeStoryContent.naFor(...)` (it **returns** the fallback rather than throwing, so there is one code path and no try/catch in the UI).
- **`RemoteOutcomeStoryService`** (future) — same interface, real remote config. Zero UI/flow churn.

**Naming:** `Local…`, not `Fake…`. `FakeAdService` is named for stubbing something that genuinely doesn't happen; this service ships real, player-visible content — it's a real local implementation of a source that will later be remote. (`NoopReminderService` follows the same honesty convention.)

### Where the two contracts live

**"N/A on failure" → inside the service.** It owns knowing whether a fetch failed, and it's the thing being swapped later; a real remote impl catches its own network/parse errors and returns the same fallback. The UI never sees an error state, never needs a retry — exactly as the founder specified.

**Min-2s loading → in the provider layer, NOT the service.** Recommended, and consistent with this codebase's own precedent: `SplashScreen` puts `Future.wait([realWork, Future.delayed(minDuration)])` in the *screen*, never inside `PreferencesService`. Reasons:
1. It's UI pacing, not data semantics. Baking it into `fetchStory` would force every future implementation to re-implement it (and a remote impl that legitimately takes 3s should take 3s, not 5).
2. `Future.wait` gives `max(fetch, 2s)`, not `fetch + 2s` — the guarantee holds regardless of source speed.
3. It keeps `OutcomeStoryService` a pure data source and independently unit-testable with no fake clock.

```
outcomeStoryProvider = FutureProvider.autoDispose.family<OutcomeStoryContent, RunSummary>(
  (ref, summary) async {
    final results = await Future.wait([
      ref.watch(outcomeStoryServiceProvider).fetchStory(summary),
      Future<void>.delayed(kMinStoryLoadDuration),   // 2s, founder-resolved
    ]);
    return results.first as OutcomeStoryContent;
  });
```

## 3. Provider shape & repeat-avoidance

**`FutureProvider.autoDispose.family<OutcomeStoryContent, RunSummary>`**, keyed by `RunSummary` object identity — the same identity-keying the current `Provider.autoDispose.family` already relies on. The screen holds the one `RunSummary` instance for its whole life, so the family entry resolves **once**: rebuilds (share toast showing/hiding, entrance animation) re-read the cached `AsyncValue` and never re-fetch or re-roll. `autoDispose` frees the entry when the screen goes away.

Do **not** add `ref.keepAlive()`: it would pin one entry per run for the session with no benefit, since the screen watches continuously for its entire lifetime.

**Repeat-avoidance moves into the service.** Today `_LastFlavorIndices` is a mutable holder in a session-scoped `Provider`, consulted by the screen-facing provider. Now that selection *is* the service's job, that bookkeeping belongs to `LocalOutcomeStoryService` as instance state, with `outcomeStoryServiceProvider` a plain (non-autoDispose) `Provider` so it lives for the session. A future remote service would do its own dedupe server-side — the interface stays clean either way.

**Which dimensions get last-shown tracking: both.** Per tier, track the last **beat** index and the last **icon** index separately (6 ints total). The icon is the single largest visual element on the card; a back-to-back repeat of a 28px emoji is at least as noticeable as a repeated sentence, and the icon pools are the smallest (4–6 entries), so repeats are *more* likely there. `StorySelector.pick` keeps today's O(1) avoid-index shift (no re-roll loop, degrades gracefully when `pool.length == 1`).

## 4. Loading state placement & navigation

**Decision: a phase *inside* `OutcomeCardScreen`, driven by `AsyncValue`. No route, no nav-graph change.**

`PlayLoopScreen`'s single `pushReplacement` to `OutcomeCardScreen(summary:)` keeps working unchanged — the screen simply renders `asyncContent.when(loading:…, data:…, error:…)`. Nothing breaks. This matches the codebase's existing `AsyncValue`-driven pattern (`playerProfileProvider` on Home) and avoids a throwaway route that would need its own `RunSummary` plumbing and a second `pushReplacement`.

**The loader is already tier-themed.** The outcome (`death`/`survived`/`eternal`) is known synchronously from `RunSummary` the instant the screen mounts — only the *content* is fetched. So the loading card uses the final tier palette immediately (dark/inverted for death), and the transition to the loaded card is a pure content swap with no jarring colour flip. This is exactly what the mockup's two loader variants (light + inverted) depict.

Loader composition (mockup): pulsing 💓, "Loading your life card…", three bouncing dots, the "Every ending is one of a thousand…" subline, and the wordmark pinned bottom — all inside the same 9:16 card silhouette so nothing shifts on resolve.

`error:` is unreachable by construction (the service returns the N/A fallback instead of throwing), but is still mapped to the same N/A card rather than left to throw — defence in depth.

**Entrance animation timing must move.** Today `_entranceController.forward()` fires in `initState`; if left there the card would animate in *behind the loader* and be static on resolve. Drive it from the loading→data transition instead (`ref.listen` on the provider, `mounted`-guarded).

**`adGateProvider.registerRunCompleted()` stays where it is** (post-frame at screen mount). It counts completed runs, not resolved cards; the 2s load must not change interstitial cadence.

## 5. Icon / emoji rendering

Display-only concern — `Text` handles all of these correctly and the **`characters` package is not needed here**. That package exists in this codebase for *counting and truncating* grapheme clusters (onboarding's 12-char name cap); we never measure, index into, or truncate the icon, so plain `String` + `Text` is correct.

Encoding notes for the mockup's specific glyphs:
- **⏰️** = U+23F0 + U+FE0F (variation selector) — multi-codepoint, not ZWJ. Renders fine; just don't `substring` it.
- **😮‍💨** (face exhaling) = U+1F62E + **ZWJ** + U+1F4A8 — a true ZWJ sequence. Renders as one glyph where supported, degrades to 😮💨 (two glyphs) where not. Acceptable.
- **😵** U+1F635 and **✨** U+2728 — single codepoint, universally safe.
- **🛟** (ring buoy, in the Survived chip) is **Unicode 14.0 (2021)** — the riskiest glyph here; it may render as tofu (□) on older Android system emoji fonts. Flagged (§7 flag 3).

Emoji resolve via the system emoji font, not Fredoka — per-glyph fallback from a `Text` with `fontFamily: 'Fredoka'` is automatic and correct on Android. On Flutter **web/CanvasKit** emoji coverage depends on the bundled fallback font; worth a visual check on the web target, though Android is primary.

Because these glyphs are also **rasterized into the shared PNG** (§6), whatever the device renders is what recipients see — a tofu box would ship into the share image. That raises the stakes on flag 3.

## 6. Reconciling with the sharing / `RepaintBoundary` mechanism

The capture mechanism is **unchanged** — `CardRenderer.renderToFile(GlobalKey)` captures whatever is inside the boundary, so a layout restructure is transparent to it. Three real consequences, though:

1. **Enforce the 9:16 aspect inside the boundary.** Today the card is an `Expanded` that fills available height, so the captured PNG's aspect varies by device. The new card is explicitly a story format (mockup 250×445 ≈ 9:16), and the whole point is sharing to IG Stories. Wrap the card in `AspectRatio(aspectRatio: 9/16)` **inside** the `RepaintBoundary` so every device produces an identically-proportioned story image. At `pixelRatio: 3` that's a comfortably high-res export.

2. **The store badges must be inside the boundary — and this now matters more than anything else in the footer.** Previously the shared image's only call to action was the `stayalive.app` wordmark. Now the App Store + Play badges do the install-driving work, and they only exist *in the image* (they're decorative, non-tappable in-app, founder-resolved — no `url_launcher`, and the App Store badge is aspirational since iOS isn't a build target). If they fell outside the boundary the redesign's central purpose — "every share is an install ad" — would silently fail. Treat "badges are inside the captured region" as a test assertion, not just an intention.

3. **Gate Share on resolved content.** The boundary stays where it is (wrapping the aspect-ratio'd card), so during loading it would capture the *loader*. Disable the Share button unless `asyncContent.hasValue`. The existing `_sharing` re-entrancy guard is unaffected. Sharing an N/A card is permitted (it's a valid, if unlucky, card) — no special-casing.

## 8. Memory-safety review

New stateful surface: an async min-duration load plus a looping loader animation, on a screen that can be navigated away from mid-flight.

1. **Navigating away mid-load.** The `Future.delayed(2s)` is not cancellable, but it captures no `BuildContext` and completes into an already-`autoDispose`d provider, where Riverpod discards the result — no setState-after-dispose, no leak. The only requirement is that nothing in the provider touches widgets (it doesn't).
2. **Loader animation disposal.** `outcome_card_loading.dart` owns exactly one `AnimationController` (`repeat()`) driving both the heartbeat pulse and the three staggered dots via `Interval`s — one `Ticker`, not four. Created in `initState`, **disposed in `dispose()`**. Because it's built inside `AsyncValue.when(loading:)`, it unmounts automatically on resolve and tears its ticker down with it.
3. **Entrance controller retiming.** Moving `forward()` out of `initState` into a `ref.listen` transition callback requires a `mounted` guard in that callback and must fire **once** (guard with a `bool _entranceStarted`) — a provider can emit more than once across rebuilds.
4. **`BuildContext`/`ref` across the async gap.** Unchanged discipline from v1 §8 / v2 §9 / v3 §11: `if (!mounted) return;` after every `await` in `_onShare` and `_onAgain`. The load itself needs none (it's declarative via `AsyncValue`).
5. **Share during load.** Gated on `hasValue` (§6.3), so `renderToFile` can never race a boundary that's showing the loader, and `CardRenderer`'s existing null-context abort still covers the screen-disposed case.
6. **`ui.Image` lifetime.** Unchanged — `CardRenderer` already disposes the image in a `finally` and overwrites one temp filename. The card getting taller (9:16 at `pixelRatio: 3`) modestly increases peak bytes during encode; still a single short-lived buffer, well within budget, and freed immediately.
7. **Selection memory bounds.** The service's last-shown state is six `int?`s for the app session — constant, tiny, and not per-run accumulating (the previous `_LastFlavorIndices` had the same footprint).
8. **Family entry accumulation.** `autoDispose` + one `RunSummary` per screen means at most one live entry at a time; entries are collected when the screen is replaced by "Again". Confirmed no `keepAlive` (§3).

## 9. Flags for founder sign-off

Most of this pass was founder-resolved up front. These are the genuinely open calls:

1. **Headline + story are bundled in one pooled entry; only the icon is independently drawn.** Independent headline/story pooling would produce contradictions like "One tap too late." over a story about tapping *early* — a clash visible between the mockup's own two death examples. If you specifically want all three dimensions independent, the headlines must be re-authored as outcome-generic one-liners ("Gone.", "That's a wipe.") that pair safely with any story — say the word and I'll respec the pools that way.
2. **Numeric placeholders `{min}`/`{peak}` supported in headline and story** (the mockup's "Saved at 3%." needs it, and the new layout deletes the old stat sub-line, so this is how run stats survive onto the card). Related: the mockup's story copy "15:98… 15:99…" is stale — it implies ~16s targets, but the resolved target range is 2.00–6.00 s. Authored copy will avoid literal clock values; confirm you don't want `{target}`/`{stop}` placeholders (they'd require extending `RunSummary`).
3. **FOUNDER-RESOLVED: swap 🛟 for a safer icon.** Confirmed — replace the Survived chip's ring-buoy (Unicode 14.0, tofu risk on older Android, baked into the shared PNG) with a universally-supported alternative. Use **🆘** (Survived chip + icon pool member) — matches the "rescue" tone and is Unicode 6.0 (2010), safe on any Android device this app targets.
4. **Name-span colour on the inverted death card.** The mockup's `.death.inv` doesn't override `.nm`, so the player's name would inherit `--red #F0483E` on the near-black `#1F2A2E` — roughly 3.5:1 contrast at 14px, legible but weak. Recommend using the lighter `#FF8A82` the mockup already defines for the inverted chip text. Confirm, or keep it strictly per-mockup.
5. **FOUNDER-RESOLVED: "Death #N of 1000" is dropped entirely.** Confirmed — matches the new mockup as designed; no catalog line anywhere in the new card anatomy. Consistent with the collection gallery already being out of scope (v3 §1 item 7).
6. **Share stays enabled on an N/A card** (it's a valid card, just unlucky). Since the failure path is unreachable while the implementation is local, this is near-theoretical — flagging only because it becomes real the day a remote source lands.

*Unchanged and explicitly not revisited:* the sharing/capture mechanism (v3 §4), ad interstitial cadence and the "Again" flow (v3 §5/§9), `RunSummary`'s shape, and the Play Loop's hand-off (`pushReplacement` to `OutcomeCardScreen(summary:)`).
