# Architecture v4

*Living document. Per the versioning convention, `vN.md` files are **never edited in place** — this file supersedes `docs/architecture/v3.md` (which stays as the historical record of the five-ask Play-Loop reconciliation). v4 is a **narrow, fast-turnaround gap-fix round**, not a re-scope: it amends exactly two things the founder flagged after reviewing the shipped v3 Play-Loop build (branch `phase2-play-loop`, PR #6 open against `main`, do **not** merge). It touches nothing else. Everything from v1/v2/v3 not named below is carried forward unchanged and is not re-argued. The next agreed revision lands as `v5.md`.*

## 0. What changed from v3, and why

The v3 build shipped and works. Two of its details are being adjusted:

1. **Gap 1 — partial reversal of v3 item 3.** v3 made the numplate a *second live scoring tap target* sharing the bottom TAP button's `_handleTap`/`registerTap` path (v3 §6.2). The founder now wants that scoring behavior walked back **for this phase**: the numplate stays touch-responsive (its `TapSurface` stays) but must do **nothing** on tap — no `registerTap`, no life change, no flash-wash, no flying-pill launch. The **bottom TAP button becomes the sole scoring input again** (the only surface that resolves a tap against the target).
2. **Gap 2 — legend pills go from a static range to a live per-band rolled value.** v3 §4.3 had the two bottom legend pills show the *range* (`"Hit +2 to +3%"` / `"Miss -5 to -3%"`). The founder wants each pill to instead show the **actual rolled value from the most recent tap of that specific band**, updating live and independently, seeded to each band's gentlest value before the first tap of a fresh run.

**What v4 does NOT touch (carried forward from v1/v2/v3, not re-argued):** the monotonic-clock-only rule; timestamp-in-`onPointerDown`; `Listener`-only tap capture; `resolve()` / `lifeDeltaFor()` stay pure and are **unchanged** (the roll mechanics from v3 §4 are correct and stay exactly as they are); the ranged-delta constants in `TimingConfig` are unchanged; Perfect stays fixed +3%; the death-ends-run detection, persisted `deathCount`, and `startNewCycle()` restart (v3 §3); the flying result pill's `AnimationController` flight (v3 §7); the flash-wash 120ms timer; the Riverpod/Hive stack; the full scope guard (still-banned adaptive tightening, still-deferred outcome-card system).

This is a **two-item amendment.**

## 1. Gap 1 — the numplate becomes a non-scoring, still-tappable surface

### 1.1 Current state (what v3 shipped)

In `play_screen.dart`, the center zone wraps `_Numplate` in a `TapSurface` whose `onTapMicros` is `_handleTap` — the **same** handler the bottom 88dp button uses. So a numplate tap runs the full scoring path: `registerTap` → life change / possible death → flash-band set → flight launch → hit/miss sound.

### 1.2 The decision — keep the `TapSurface`, make its callback a true no-op

**Decision: keep the second `TapSurface` wrapper around the numplate, but give it an empty `onTapMicros` callback (`(_) {}`). Do NOT remove the wrapper, and do NOT route it to `_handleTap` or any other scoring path.**

Mechanism, exactly:

```dart
TapSurface(
  clock: clock,
  // v4 gap 1: the numplate is deliberately tappable-but-INERT this phase.
  // It MUST NOT score — no registerTap, no life change, no flash, no
  // flight. The bottom TAP button is the sole scoring input (v4 §1). This
  // empty callback is intentional and load-bearing, NOT half-wired/dead
  // code: the TapSurface is kept so the number still absorbs touches (a tap
  // on the number reads as "pressed but nothing happened", never falls
  // through to a surface behind it) and as a forward-compatible placeholder
  // for a possible future *non-scoring* numplate action. Do not "fix" this
  // by wiring it back to _handleTap.
  onTapMicros: (_) {},
  child: Padding(
    padding: const EdgeInsets.symmetric(horizontal: 28, vertical: 24),
    child: _Numplate(key: _numplateKey, targetSeconds: targetSeconds),
  ),
)
```

### 1.3 Why keep the `TapSurface` rather than remove it (the justification the task asks for)

**Recommendation: keep it, as an empty-callback no-op.** Three reasons, in priority order:

1. **Founder directive.** The founder explicitly wants the numplate to "remain tappable/clickable" — i.e. it must still respond to touch (`HitTestBehavior.opaque` still absorbs the press), just without a scoring effect. An empty callback satisfies this exactly; removing the wrapper would make the number a dead region.
2. **Touch containment.** Keeping the opaque `TapSurface` means a press landing on the number is *consumed there* and reads as "pressed, no effect," rather than passing through to whatever sits behind it in the tree. That is the honest behavior for "tappable but does nothing," and it's what the founder described.
3. **Forward-compatible placeholder.** It reserves the numplate as a wired-up surface for a plausible future *non-scoring* interaction (e.g. an inspect/hint gesture) without re-introducing a `Listener` later. The diff to re-activate is a one-line callback swap.

**Why not the alternatives:**
- *Remove the `TapSurface` entirely (make the number inert at the widget level):* rejected — contradicts the founder's "keep it tappable" instruction, and makes the number a fall-through region.
- *Keep routing to `_handleTap` but early-return for the numplate:* rejected — that's exactly the "dangling half-wired second `TapSurface` that looks like it should do something but silently doesn't" trap the task warns against. The two surfaces would share a handler where one branch is a silent no-op — far more confusing than a visibly empty callback with a load-bearing comment.

**The `GlobalKey` (`_numplateKey`) stays on `_Numplate` regardless of gap 1** — it is the flying pill's *arrival anchor* (v3 §7.3) and has nothing to do with the numplate's tap behavior. Gap 1 must not remove it.

### 1.4 Anti-dangling-wire requirement (the task's explicit concern)

To ensure the no-op reads as **intentional**, not broken:
- The empty callback carries the explanatory comment above (load-bearing — `code-reviewer` should treat its removal as a regression).
- `_handleTap`'s own doc comment currently says it is the "Shared tap handler for BOTH tap surfaces." **Update it** to state that as of v4 it is the bottom TAP button's handler only; the numplate's `TapSurface` is intentionally inert.
- The defensive `phaseBeforeTap != RunPhase.playing` guard inside `_handleTap` stays (it's cheap and still correct), but its comment about "both TapSurfaces" should be trimmed to reflect the single caller.

## 2. Gap 2 — legend pills show a live, per-band, per-tap rolled value

### 2.1 The behavior (founder-confirmed)

- The **Hit pill** shows the life-delta the **most recent On-point tap** actually rolled. On-point rolling +2% → `"Hit +2%"`; the next On-point tap rolling +3% → `"Hit +3%"`.
- The **Miss pill** shows the life-delta the **most recent Miss tap** actually rolled, updating independently — an On-point tap never touches the Miss pill, and vice versa.
- **Perfect touches neither pill.** Perfect is fixed +3%, has no range, and is not represented by either legend pill (v3 §4.1). A Perfect tap leaves both pills exactly as they were.
- **Seed default (founder-confirmed, settled — see §5):** before the first tap of a given band in a fresh run/cycle, that band's pill shows the band's **gentlest** value as a seed — `"Hit +2%"` and `"Miss -3%"` — not the full range, not a blank.

### 2.2 The `RunState` shape change — two new per-band fields

The existing `lastLifeDelta` / `lastBand` pair tracks **the single most recent tap regardless of band** (the flying pill and flash-wash need "what did the last tap do"). Gap 2 needs **independent memory per band** — "what did the last *On-point* tap do" and "what did the last *Miss* tap do" — which the single-most-recent pair cannot express (an On-point tap followed by a Miss tap must leave the Hit pill showing the On-point value). So this is genuinely new state, not derivable from `lastLifeDelta`/`lastBand`.

Add two fields to `RunState`:

```dart
/// The life-delta the most recent On-point ("Hit") tap actually rolled —
/// drives the "Hit" legend pill (v4 §2). Distinct from `lastLifeDelta`
/// (the single most-recent tap regardless of band): this is per-band
/// memory, unchanged by a subsequent Miss or Perfect tap. Seeded to
/// `_seedHitLifeDelta` (+2, the band minimum) in `build()`/`startNewCycle()`
/// and never null — the pill always has a value to show.
final double lastHitLifeDelta;

/// The life-delta the most recent Miss tap actually rolled — drives the
/// "Miss" legend pill. Seeded to `_seedMissLifeDelta` (-3, the band's
/// least-negative bound). Same per-band-memory semantics as above.
final double lastMissLifeDelta;
```

Both are **non-nullable `double`** (not `double?`): the founder-confirmed seed default means these always have a display value, so nullable + placeholder logic would be dead complexity. Add both to the constructor and to `copyWith` (as `double?` params with the `?? this.field` pattern, matching the existing fields — passing `null` keeps the prior value, so a Miss tap updates only `lastMissLifeDelta` and leaves `lastHitLifeDelta` untouched, which is exactly the independence gap 2 requires).

### 2.3 The seed constants — and the naming trap that MUST be got right

The seed is each band's **smallest-magnitude** (gentlest) value:

```dart
// v4 §2.3. NOTE THE ASYMMETRY — this is the one easy bug in gap 2:
//  - Hit seed  = onPointLifeDeltaMin (+2.0): min IS the gentlest gain.
//  - Miss seed = missLifeDeltaMAX  (-3.0): for Miss, max (-3, the LEAST
//    negative bound) is the gentlest loss. missLifeDeltaMin is -5.0 (the
//    HARSHEST loss) — seeding Miss to that would be wrong and would show
//    "Miss -5%" pre-first-tap instead of the founder-confirmed "Miss -3%".
const double _seedHitLifeDelta = TimingConfig.onPointLifeDeltaMin;  // +2.0
const double _seedMissLifeDelta = TimingConfig.missLifeDeltaMax;    // -3.0
```

These derive from the existing `TimingConfig` constants (single source of truth) — **no `TimingConfig` change is needed for gap 2** (`onPointLifeDeltaMin`/`missLifeDeltaMax` already exist from v3 §4.4). The founder's literal "Hit +2% / Miss -3%" reconciles to these two bounds.

### 2.4 `RunController` changes

**`build()`** and **`startNewCycle()`** both construct a fresh `RunState` directly — each must set the two new fields to their seeds:

```dart
lastHitLifeDelta: _seedHitLifeDelta,
lastMissLifeDelta: _seedMissLifeDelta,
```

This satisfies the task's reset question directly: **yes, `startNewCycle()` must reseed both fields to their minimums.** Because `startNewCycle()` builds a brand-new `RunState` (it does not go through `copyWith`), the last cycle's rolled values cannot carry over — the reseed is explicit and unconditional. `deathCount` remains the only field deliberately carried across cycles.

**`registerTap()`** — in the band-resolved section, update only the field matching the tap's band. Cleanest expression: derive the two next values inline off `result.band`, then pass them into the existing `copyWith` (both the normal branch and the death branch):

```dart
final double nextHit =
    result.band == TimingBand.onPoint ? result.lifeDelta : state.lastHitLifeDelta;
final double nextMiss =
    result.band == TimingBand.miss ? result.lifeDelta : state.lastMissLifeDelta;
// Perfect => both keep their prior value (Perfect touches neither pill).
```

Then add `lastHitLifeDelta: nextHit, lastMissLifeDelta: nextMiss` to **both** the death-branch `copyWith` and the normal-branch `copyWith`.

- **Death branch:** a fatal tap is always a Miss (life only reaches 0 via a negative delta), so it updates `lastMissLifeDelta`. This value is **not user-visible** (the screen switches to the death placeholder, and `startNewCycle()` reseeds before the pills are shown again), but updating it keeps the two branches uniform and avoids a special-case. Documented as intentional; not a founder-facing question.
- **No-op path:** `registerTap` still early-returns when `phase != playing`, so a tap outside `playing` touches neither field. Unchanged from v3 §3.3.

### 2.5 `play_screen.dart` changes — the pills read state, not the range

The two `_LegendPill`s currently source their labels from `_formatLifeDeltaRange(TimingConfig...)`. Change them to read the live `RunState` values (`runState` is already `ref.watch`ed at the top of `build()`, so the pills rebuild on every tap for free):

```dart
_LegendPill(label: 'Hit ${_formatSignedLifeDelta(runState.lastHitLifeDelta)}%'),
_LegendPill(label: 'Miss ${_formatSignedLifeDelta(runState.lastMissLifeDelta)}%'),
```

`_formatSignedLifeDelta` is **unchanged** and already produces `"+2"` / `"-3"` (the pill appends the `%`), so `"Hit +2%"` / `"Miss -3%"` fall out directly. `_LegendPill`'s own chrome is unchanged.

**`_formatLifeDeltaRange` becomes dead code** once the pills stop calling it. Remove it and its doc comment in the same PR (it has no other caller) so v4 doesn't leave an orphaned range-formatter that implies the old behavior still exists. `code-reviewer` / `refactor_tool` should confirm no remaining references.

## 3. Interaction with the flying-pill flight and the flash-wash — confirmed unaffected

The task requires confirming neither gap disturbs the v3 flight/flash machinery, and that gap 1 leaves no half-wired surface. Confirmed:

- **Flash-wash (`tapFlashBandProvider` + 120ms `Timer`)** is set **only inside `_handleTap`**. After gap 1, `_handleTap` is called **only by the bottom TAP button**. A numplate tap runs the empty `(_) {}` callback and never touches the flash provider. So the wash still fires exactly once per *button* tap, never from the numplate. Correct and unchanged.
- **Flying result pill (`_launchFlight`)** is likewise called **only inside `_handleTap`**, so it launches only on a button tap. Its **arrival anchor is still `_numplateKey`**, which stays on `_Numplate` (§1.3) — so the pill still flies button→numplate exactly as in v3. Gap 1 changes what the numplate *does on tap*, not where it *is*, so the flight geometry is untouched.
- **`IgnorePointer` on the flight layer** stays (v3 §7 / play-loop-v3 §1.6). It was there so a mid-flight pill can't eat a tap; that property is orthogonal to gap 1 and remains.
- **Gap 2** touches only `RunState` fields and two label strings — it adds no timers, no animation, no provider. The pills already rebuild via the existing `ref.watch(runControllerProvider)`. No interaction with the flight/flash clocks at all.
- **No dangling wire:** the numplate `TapSurface`'s inert state is made explicit by the load-bearing comment (§1.2) and by updating `_handleTap`'s doc to name the button as its only caller (§1.4). It does not "look like it should do something but silently doesn't."
